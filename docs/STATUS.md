## ✅ 세션 14 = 만드는 세션 — **중첩 진 (재귀) 구현**

> **"복합마법이냐 재귀마법이냐" → "둘 다 (룬끼리=복합, 진끼리=재귀)"** — 사용자, 2026-07-15.
> 이번 세션은 **진끼리=재귀**를 만들었다 (룬끼리=복합은 다음). 모델·근거는 TRUTH §4 + [[takbon-nested-circle-model]].

**모델 (확정):** 진 = 완성된 마법 유닛(모양+룬+문양). **진 안 진 = 껍질이 내용물을 착탄점에 배달**
(재귀). 껍질이 착탄·벽·수명 끝에 죽으면 품은 진들이 그 자리에서 각자 전개. 배치가 의미(안=배달/옆=형제/화살표=방향).

**구현 (그리기 → 발사 끝까지, 깊이 N 재귀):**
1. **스키마** `SpellDesign.children: Array[SpellDesign]` — Resource 기본값이 곧 마이그레이션(옛 .tres 자동 로드). `.tres` 재귀 라운드트립 검증.
2. **해독** `design_builder.assemble_tree/build_tree` — "감싸는 가장 작은 진"으로 트리 조립. 각 획을 소속 원 컨텍스트로 기존 인식기에 재통과(룬/문양 규칙이 원마다 그대로). 단일 원이면 기존과 동치.
3. **캔버스** `drawing_canvas` — 원은 언제나 새 노드로 수락. 단계·수락이 **활성 노드(방금 그린 원)**를 따라 안쪽 진의 룬을 받는다. 원 1개면 기존 경로 100% 보존(안전 분기).
4. **발사** `projectile._consume`(착탄·벽·수명 끝 통합) → `deploy_children` 시그널 → `spell_system._spawn_for`가 자식을 그 자리에 단발 전개(지연 실행, 재귀 연결). 지팡이 패턴은 최상위 껍질만.

**② 룬 N개 = 복합 (같은 세션 추가):** 한 진에 서로 다른 룬 여럿 → **한 탄에 속성 합침.**
- 스키마 `RuneInstance` + `SpellDesign.runes` + `rune_list()` 폴백(구세이브=스칼라 하나). class_name 추가라 `--import` 1회.
- 위력 = **fill 가중평균**(룬 1개면 그 룬 그대로) · 상태이상 = **룬마다 각각** 실림.
- **적 계약 무변경**: primary(fill 최대)가 `take_hit(피해,…)`, 나머지는 `take_hit(0,…)`로 상태만(`if dmg>0` 덕에 이중계산 없음). *"적 바꿀 필요 없다"(사용자) 지킴.*

**③ 예시 카탈로그 (F6 시험대):** `src/core/example_designs.gd` — 예시 5종(단일·복합 불+물·복합 불+충격·중첩 충격→불·중첩 바람껍질→불+물)을 **손으로 구성**(인식기 안 태움 = 견고).
- **책 닫힘 + 숫자키** = 불러와 **바로 발사**(0=해제). 그리기 없이 복합·중첩 확인.
- **책 펼침 + 숫자키 = 탁본 필사** — 완성 도안을 **옅은 탁본**으로 캔버스에 깔고 그 위에 따라 그린다(게임의 심장 = 탁본). `canvas.show_rubbing/clear_rubbing`(순수 배경, _entries·인식 무관) + `forge_panel.example_requested` 시그널. 중첩은 자식까지 겹쳐 깔린다.

**테스트 (신규, 조용히 안 죽게 목록 편입):** `test_drawing_auto` +트리·캔버스(315/315) · `test_spell_auto` +`_test_nested_deploy`·`_test_composite_runes`(불+물→BURN+WET)·`_test_example_catalog`. **전 16스위트 그린(필드·UI 포함).**

**아직 안 한 것:** 캔버스로 **다중 룬 그리기**(단일 원 acceptance 게이팅 — 지금은 카탈로그로 테스트) · 중첩 그리기 손맛(UX "노드 완성형" 임시) · 마나·잉크 진마다 합산 · B1 수증기·B3 속성효과(이제 복합·재귀 다 열려 성립 가능).

## 세션 12 — 방향이 지팡이로 옮겨갔다 (v2.0) · **GDD 승격 + 구현 병행**

### 사용자 지적에서 시작해 **역할 축이 다시 재배분됐다**

세션 11이 "고민 중"으로 남겨 둔 항목(*"앞뒤옆 이게 좀 복잡함. 그냥 마우스 방향으로 나가도록 해야
할 듯"*)에 사용자가 답을 냈다:

> **"마법 발사를 그냥 지팡이로 대체하자. 결국 보는 방향으로 발사가 맞고, 지팡이에 따라 여러 발이
> 나가거나 내 주변에서 전체 방향으로 나가거나가 정해짐."**

**바뀐 건 한 줄이다: 방향이 문양에서 지팡이로 갔다.** 나머지는 전부 그 연쇄다 — BACKLOG §0이
진단해 둔 대로 문양은 "방식+세기" 둘이 아니라 실은 **방향·기점까지 몰래 쥔 네 개짜리 부품**이었고,
방향을 떼어내자 발수도 같이 갈 곳이 없어졌다. **발수 + 방향을 받는 새 부품(지팡이)이 생겼다.**

리드가 되물었을 때 사용자가 정리한 것:
- **진 모양**: *"투사체의 모양이 진이라고 끝인데? 그냥 방향을 마법지팡이로 옮긴 게 끝이여"* —
  진은 이제 "출구의 지형"이 아니라 **탄의 생김새**(히트박스 포함)
- **룬 N개**: *"룬은 하나의 진 안에 들어가 있음. 진 안에 고유한 룬은 하나만 가능한 걸로 하고…
  불과 물의 룬을 가지고 있으면 쏘는 순간 증발하게 할 거 같아"* — 증발이 벌인지 보상인지는
  **"전투에서 확인할 듯… 그 자리에 수증기가 남는 느낌일 듯한데?"** — **미정으로 남았다**
- **문양 어휘**: 팅김⚡·유도∿·관통‖ 유지 + **증폭·응집 추가** (이름만 확정, 효과 수치는 미정)
- **지팡이 × 도안**: 지팡이 1개 + 도안 4장 — 기존 장착 구조(완드 슬롯) 그대로
- **스코프**: *"일단 지금은 그냥 지팡이만. 이번 주 목표는 그린 대로 마법이 나가게 하는 거임"*

### 구현된 것 (리드가 src를 직접 고침 — 이 세션 문서 작업과 병행)

### 노바가 죽지 않았다 — **지팡이로 이사했다** (당초 우려가 뒤집힘)

세션 11까지는 "문양 8개를 방사형으로 그려 만드는 노바 도안이 지팡이 도입으로 죽는다"는 우려가
있었다. **실제로는 지팡이(`wand_ring`)가 그 역할을 대신 가져갔다** — 잃은 건 "문양 배치로 직접
설계하는 정밀함", 얻은 건 **"잉크를 한 방울도 안 쓰고 전방위가 나온다"**는 것. v1.9 §4.3이 적어 둔
*"전방위는 두 갈래: 문양 여러 개(잉크↑, 정밀) vs 별 진(잉크↓, 균등)"* 교환에서 **별 진의 자리를
지팡이가 대신 가져갔다** — 별 진(구조 축)이 더 이상 급하지 않은 진짜 이유이기도 하다.

#### 핵심 논리 — **기둥은 규칙이 아니라 결과다**

규칙은 **"화살표 = 충격파 하나가 가는 방향"** 하나뿐이다. **기둥·폭발을 코드로 정의하지 않았다** —
충격파끼리 부딪히면 저절로 나온다. GDD §4.1이 남긴 문장(*"별 진 = 전방위… 별을 그리면 별처럼
퍼진다"*, v1.8, 지금은 폐기)과 **정확히 같은 원리**로 이어 붙였다.

- ⚠ **"수렴하면 기둥"이라고 코드에 적지 않는다** — 적는 순간 창발이 아니라 규칙이 되고, "몇 개부터
  기둥인가"라는 답 없는 질문이 따라온다
- **리드 실측**: 진 둘레 화살표 8개가 **밖**을 겨누면 충격파 8개·**기둥 0개** / **룬(중심)**을
  겨누면 충격파 8개·**기둥 2개**(중심에서 저절로 만났다) — 실제로 "규칙 없이 결과가 나온다"가
  관측으로 확인됨

#### 부활한 필드 + 방위 기준

**탄이 곧 진**이므로(v2.0), 적에 닿는 순간 진이 히트 지점에 놓이고 진 위 화살표들이 각자 제자리에서
제 방향으로 충격파를 뿜는다 — 종이 위의 배치가 그대로 착탄 그림이 된다.

| 필드 | v2.0 | **v2.1** |
|---|---|---|
| `ArrowData.origin` | 소비 중단 | **충격파의 시작 자리** (진 위 그 위치) |
| `ArrowData.direction` | 소비 중단 | **충격파가 가는 방향** |
| `SpellDesign.aim_axis` | 소비 중단 | 여전히 소비 중단 — 개념만 상수(`UP_AXIS`)로 살아남는다 |

**방위 기준 = 탄이 가던 방향** (종이 절대 기준이 아니다). 종이 위쪽 = 탄이 가는 쪽이므로 위로 그은
화살표는 적을 **밀어내고**, 아래로 그은 화살표는 **나에게 끌어온다.** 종이 절대 기준을 안 쓴 이유:
같은 도안이 적 위치에 따라 끌어오기도 밀어내기도 하면 **내 통제 밖**이 된다.

```gdscript
# 회전량은 하나이고 위치·방향에 똑같이 적용된다
var rotate_by := travel_angle - DesignBuilder.UP_AXIS   # UP_AXIS = -PI/2
충격파 시작 = 히트지점 + (arrow.origin * 탄 반지름px).rotated(rotate_by)
충격파 방향 = arrow.direction + rotate_by
```

🔴 **세션 7의 "90도 틀어짐"이 정확히 이 공식 자리에서 났었다** — `direction`은 캔버스 절대각이고
회전은 발사 때 **한 번만** 건다. 두 번 걸지 말 것 (TECH_SPEC §4.0-b에 명문화).

⚠ **방위 가이드(앞·뒤·좌·우)가 되살아났다.** v2.0에서 "종이에 방위가 없어졌다"며 지웠는데
(위 세션 12 전반, "UI가 낡은 규칙을 가르치고 있었다" 표), **충격파가 그 자리를 다시 채웠다.**
의미는 매번 달랐다 — **v1.5 발사 방향 → v2.0 폐지 → v2.1 충격파 방향** (세 번째 의미).

- → `InkRender.arrow_heading()` = **시작점 → 최원점**(창끝). **core에 한 곳으로 모았다** —
  인식기와 먹선 렌더가 같은 공식을 **각자 복제**하고 있어서 발사각과 그림이 **함께** 틀어졌다
- **왜 163건이 초록이었나**: 문양 테스트가 *"어느 글자인가"*만 보고 **방향은 아무도 안 봤다.**
  인식률 100%인 채로 관통탄만 빗나갔다. 세션 7의 "90도 틀어짐"과 **같은 구멍**

**2. `reach`가 "구불구불함"을 재고 있었다** (보정 작업 중 파생 발견)

`reach`(사거리·반사수·관통수)를 획의 **총연장**으로 쟀다. 그건 *"얼마나 멀리 뻗었나"*가 아니라
**"얼마나 구불구불한가"**다. 실측 — 전부 똑같이 **0.40을 뻗었는데**:

| 문양 | 총연장 기준 reach | 반사 |
|---|---|---|
| 기본 (직선) | 2.00 | 3회 |
| 팅김 진폭 크게 | **3.00 (상한 포화)** | **4회** |
| 팅김 촘촘히 8꺾임 | **3.00 (상한 포화)** | **4회** |

**짧게 그려도 진폭만 키우면 최대 사거리·최대 반사를 공짜로** 받았고, 팅김⚡·유도∿가 기본보다
구조적으로 유리했다. → `InkRender.arrow_extent()` = **뻗은 거리**(방향과 **같은 점**을 겨눈다).
같은 거리를 뻗으면 모양이 뭐든 reach가 같아졌다 (**50% 차 → 3.8%**).
**세션 9의 `rune_fill`(AABB → 무게중심 최원거리) 수정과 정확히 같은 성격** — 정의가 불변량이
아니면 숨은 최적 플레이가 생긴다.

**둘 다 회귀 테스트로 못 박았고, 옛 코드로 되돌려 실제로 FAIL이 뜨는지 확인했다**
(`_test_heading` 상한 8도 / `_test_reach_shape_invariant` 상한 8%).

## 세션 10 — 문양에 어휘를 (v1.9) · 🎉 **역할 축 3개가 전부 찼다** (문서 확정 · 구현 전)

### 사용자 결정 — **"문양 = 발동 방식·부가 효과. 이걸로 해야할 듯"**

v1.8의 잠정안(**문양 = 궤적, 외우는 글자 없음**)을 **뒤집었다.** 문양은 **글자**다.
GDD가 지적한 딜레마 — *"그린 모양=궤적과 그린 모양=글자는 같은 획에 못 얹는다"* — 는 옳았고,
**사용자가 반대쪽을 골랐다.**

| | v1.8 잠정 (폐기) | **v1.9 확정** |
|---|---|---|
| 문양 모양 | 궤적 (그린 대로 날아감) | **발동 방식** — 팅김⚡ · 유도∿ · 관통‖ + **기본**(글자 아닌 직선) |
| 문양 길이 | 궤적을 따라가는 거리 | **길이 ÷ 진 반지름 = 사거리 배율 + 그 글자의 세기** |
| 문양 N개 | 발수 | **1개 = 1발, 각자 자기 방식** |

### 규칙을 하나도 안 늘리고 **미결 3건이 함께 풀렸다**

1. ✅ **"팅긴다"(벽 반사)** — v1.8이 *"진 모양으로도 궤적으로도 표현이 안 된다, 별도 축이 필요할 수
   있다 — 억지로 정하지 않는다"* 며 미뤄 둔 항목. **문양 글자 하나로 끝났다. 미루길 잘했다**
2. ✅ **룬 각도** — 룬 2개 + 문양 2개일 때 *"어느 탄이 불인가"*를 **룬을 진 안 어디에 두었는가**가
   답한다. 왼쪽 룬이 왼쪽으로 나가는 문양을 지배한다 (**배선**). 룬 1개면 전부 그 룬 → **하위 호환**
   - 🔴 **함정을 피해 갔다**: 쓰는 값은 **룬이 놓인 위치의 방위각**이지 `indicative_angle()`
     (글리프 회전각)이 **아니다.** 회전각을 썼다면 **불△은 3회 대칭이라 120도 돌려도 눈에 똑같아**
     플레이어가 영원히 알 수 없었다 (BACKLOG가 경고한 그대로). **위치는 눈에 보인다**
3. ✅ **룬 2개의 피해 계수** — `fill` 가중 평균 (룬 1개일 때 지금과 **정확히 같다** → 하위 호환)

### 🔴 두 층이 갈라졌다 — 사용자 질문이 잡아냈다

사용자: *"진을 뚫을 수 없는데? 문양은?"* (설치형을 논하다가)

**"진을 뚫고 나간다"는 종이 위의 문법이지 탄의 행동이 아니다.** v1.8까지 문양이 **직선 화살표
하나뿐**이라 "뚫고 나간 획 = 앞으로 날아가는 탄"이 딱 겹쳐 **두 층이 같은 것처럼 보였다.**

```
[종이 위]  획이 진 안에 머물면 → 룬        ← 인식기의 판정 기준 (문양이기 위한 조건)
           획이 진을 뚫고 나가면 → 문양
[전투]     그 문양의 글자가 정한 대로 발동   ← 별개 층. 팅김은 획은 곧게 나가지만 탄은 튕긴다
```

**이 구별이 없으면 "설치형은 안 날아가니까 문양이 아니다"라는 잘못된 결론에 도달한다.**
GDD §4.0에 명시했다.

### 세 부품이 **같은 문법**이 됐다 (v1.9의 부수 이득)

| 부품 | **모양** = 무엇을 | **크기** = 얼마나 (÷ 진) |
|---|---|---|
| 진 | 구조 (원·별·용) | 규모 (위력·탄 크기·기준 사거리) |
| 룬 | 속성 (원소) | 농도 (상태이상 세기) |
| **문양** | **발동 방식** (팅김·유도·관통) | **세기** (사거리 배율·반사 횟수…) |

**배울 규칙이 셋이 아니라 하나다.** 그리고 크기가 셋 다 **진 대비 비율**이라 잉크 상한이
자연히 제동을 건다 — 진을 키우면 룬도 문양도 그만큼 키워야 하고, 종이가 그걸 못 버틴다.

### 포기한 것 · 얻은 것

- **포기: 임의의 곡선 궤적** (BACKLOG §3 폐기). 잃은 건 **"내 맘대로 S자"** 하나 —
  **궤적은 글자가 정한다** (유도는 휘어 따라가고, 팅김은 꺾인다).
  `ArrowData.path`는 **먹선 렌더 전용**으로 남는다 (세션 7의 "그린 획이 날아간다" 연출은 유지)
- **얻음: 문양도 탁본으로 배우는 어휘가 됐다** → 지식 습득 루프가 **진·룬·문양 셋으로 분산**
  (§11 리스크 4 추가 완화)
- **하위 호환 완벽**: 아무 글자도 아닌 직선 획 = **기본 탄**(폴백, 거부 아님). 튜토리얼 첫 도안
  (화살표)이 그대로 유효하다
- **마나에 문양 사거리 축 추가** (§5) — 공짜면 "문양은 언제나 최대한 길게"가 유일한 정답이 된다

## 🟢 세션 10 후반 — **문양 축 구현 완료** (전 스위트 그린 · 미커밋)

**순서를 바꿨다** (GDD의 "$P 먼저"를 뒤집었다 — 근거가 문양엔 해당 안 됐다):
$P를 먼저 갈라는 이유는 *"1획용으로 구부린 글자는 다획에서 다시 그려야 한다"*였는데,
**팅김(지그재그)·유도(호)·관통(창)은 애초에 1획이 자연스럽다.** 구부릴 게 없다.
**다획이 진짜로 필요한 건 진(별·용)뿐이다.** → 문양을 먼저 구현해 **눈으로 볼 수 있게** 했다.

### 어휘 — 셋 다 1획, **서로 위상이 다르다**

| 문양 | 형태 | 거동 | 길게 그으면 |
|---|---|---|---|
| **기본** | 곧은 직선 (**글자 아님 — 폴백**) | 곧게 | 멀리 |
| **팅김⚡** | 지그재그 | **벽 반사** | 더 여러 번 튕김 |
| **유도∿** | 한쪽으로 휜 호 | **적 추적** | 더 오래 쫓음 |
| **관통‖** | 직선 + 끝 화살촉 | **적 관통** | 더 많이 뚫음 |

- **U턴 형태는 못 쓴다** — 끝점이 시작점 근처로 오면 `detect_escape`가 "진을 안 뚫었다"로 읽어
  **룬으로 오인**한다. 기존 기하 규칙이 어휘를 제약한다 (좋은 제약)
- **인식 실패 = BASIC 폴백. 문양은 거부하지 않는다** (진을 뚫고 나간 획은 무조건 탄이다)

### 🔴 인식기가 선제적으로 잡은 함정 — **직진성으로는 못 가른다**

**실측(손그림 6000샘플): 직진성은 BASIC(0.868~1.000)과 유도∿(0.673~0.909)가 겹친다** —
곡률이 완만한 호는 경로가 거의 안 늘어나기 때문이다. 대신 **현 이탈도**(chord_bow = 현에서
벗어나는 최대 수직거리 ÷ 현 길이)를 쓰면 **BASIC 0.003~0.059 vs 글자 0.112~0.443,
빈 구간이 통째로 비어 있다.** → `GLYPH_MIN_BOW = 0.08` (룬의 감김 밴드를 잡은 것과 같은 수법).

**이 게이트가 없으면 실제 버그가 난다**: `scale_to_square`가 얇은 획의 세로 지터를 bbox 높이로
나눠 **화면 가득한 가짜 지그재그로 부풀려**, 살짝 흔들린 직선이 팅김⚡에 붙는다 —
**튜토리얼 화살표가 팅김이 된다.**

**또 하나**: 룬·문양 템플릿 배열을 **분리해야 한다** — 두 enum의 정수값이 겹친다 (`FIRE=0=BASIC`).
한 배열에 섞으면 조용히 서로를 먹는다.

## 세션 9 — 룬에 농도 축 (v1.7) · **역할 축 3개 중 2개 완성**

### 사용자 질문 "룬이 뭘 정해야 할까?" → **진단이 뒤집혔다**

룬은 **이미 속성 축을 갖고 있었다** (`rune_type` → 원소·상태이상이 실제로 나감). 빈 건 다른 곳이었다:
**룬을 어떻게 그리든 결과가 같았다.** $1이 크기·회전을 정규화하니 크게 그리든 작게 그리든 같은 룬이고
잉크만 더 먹었다 — **룬 그리기가 기계적으로 "메뉴에서 4지선다 찍기"였다.**
게다가 유일한 변수 `rune_accuracy`는 **위력**에 물려 있었는데, 위력은 진의 축이다 (**축 위반**).

### 확정 (사용자 결정) — **룬 크기 = 속성의 농도**

`SpellDesign.rune_fill` (0..1) = **룬 bbox 반경 ÷ 진 반지름** — "룬이 진을 얼마나 채우는가".

| | 정하는 것 | 안 정하는 것 |
|---|---|---|
| **`rune_fill`** | **상태이상 세기** — 화상 초당딜·젖음 둔화·넉백 거리·흐름 | **위력** (진의 축) |
| **`rune_accuracy`** | **속성 순도** (하한 0.6) | **위력** (v1.7에서 분리 — 축 위반 해소) |

- **위력 = 진 규모 × 룬 계수**뿐이다. "크게 때리기"와 "깊이 물들이기"가 **다른 선택**이 됐다
- **비율이라서 조합이 생긴다**: 진을 키우면 같은 룬도 농도가 내려간다(실측: 진 0.15→0.45일 때
  같은 룬의 fill 0.69→0.23). 큰 마법을 진하게 물들이려면 룬도 그만큼 키워야 하고, **잉크 상한이
  그걸 막는다** — 진·룬·문양이 종이 한 장 안에서 경쟁한다
- **마나 = 룬 + 진 규모 + 발수 + 룬 농도** (`rune_density_mana_mult` 신설). 농도가 공짜면
  "룬은 언제나 최대한 크게"가 유일한 정답이 된다
- 인식기가 이미 "룬은 진 안 / 문양은 진 밖"으로 가르므로(`ARROW_ESCAPE_R=1.05`) **비율은 자연히
  0~1에 갇힌다** — 인위적 밴드가 필요 없었다

### 🔴 잡은 버그 — **물 룬은 농도를 올려도 아무 일도 안 일어났을 것**

`enemy_base.gd`의 젖음 둔화가 `status_power`를 **완전히 무시**하고 `WET_SLOW` 상수를 쓰고 있었다
(BURN·KNOCKBACK·FLOW는 멀쩡히 power를 소비 중). 물~은 **갑주 갑충의 지정 카운터**라 이대로 두면
룬 4종 중 하나가 새 축에서 통째로 빠진다. → 둔화를 power 비례로(바닥 0.30 — 멈춘 적은 적이 아니다).
**기준 농도(fill 0.5·순도 1.0)에서 기존 `WET_SLOW` 유지** → 기존 밸런스 무변경.
젖음 **여부**(`has_status`) 판정은 그대로라 **갑주 무력화는 안 깨진다** (약한 물도 갑주는 연다).

### 🔴 회전 버그 — **룬을 돌려 그리면 농도가 증발했다** (사용자 질문으로 발견)

사용자 질문: *"만약 룬을 돌려서 그리면 어케됨?"* → **$1은 회전 불변인데 `rune_fill`은 아니었다.**
초안이 룬 반경을 **축 정렬 bbox(AABB)의 긴 변**으로 쟀는데, AABB는 회전하면 변한다.

- **실측**: 물~처럼 가늘고 긴 획을 45도로 눕히면 **fill 0.80 → 0.57 (−29%)**. 삼각형은 등방적이라
  3.5%만 흔들려 눈에 안 띄었다 — **가늘고 긴 룬(물~·충격>)일수록 심하다**
- **같은 룬으로 인식되는데 세기만 조용히 달라진다.** 플레이어는 이유를 알 수 없고, 알아내면
  "룬을 축에 맞춰 그리기"라는 **숨은 최적 플레이**가 생긴다
- → 룬 반경을 **무게중심 → 최원점 거리(외접 반경)** 로 교체. **회전 불변**이고, 가늘고 긴 획도
  과대평가하지 않는다(길이 L → 반경 L/2, AABB 긴 변과 동일). AABB의 장점은 그대로 두고 결함만 제거
- **회귀 테스트 신설** — 15·30·45·60·90·137도 회전 시 fill 편차 **0.000000** 확인
- ⚠ **테스트가 버그를 못 박고 있었다**: `test_paper_auto`의 룬 획이 하필 45도 직선이라 AABB 기대값
  0.5를 검증 중이었다 (참값 0.707). 테스트가 초록이어도 정의가 틀리면 소용없다는 사례가 또 나왔다

### 🔴 놓칠 뻔한 부작용 — **위력 인플레** (에이전트 보고로 발견)

`compute_damage`에서 `rune_accuracy`(0.6~1.0) 곱을 떼자 **곱하던 값이 사라져 위력이 통째로 올랐다** —
잘 그린 도안 **+11%**, 막 그린 도안 **+67%**. 축 분리는 의도했지만 **위력 인플레는 의도한 적 없다.**
→ `projectile_base_damage` **10.0 → 9.0**으로 기준을 0.9배 낮춰 **잘 그린 도안(accuracy≈0.9)의 위력을
v1.6과 같게 되돌렸다** (실측 진 0.2 → **5.67** / 진 0.9 → **11.34** — v1.6의 5.7 / 11.3과 일치).

**남는 의도된 변화**: 이제 **막 그린 도안도 같은 위력**이 나온다. 그게 축 분리의 요지다 —
엉망으로 그린 대가는 위력이 아니라 **속성 순도**(상태이상 세기)로 치른다. 플레이 검증 관찰 항목.

사용자 지적: *"그린 대로 날아가는 게 아니라 **조합한 마법**이 나가는 거다. 그리는 건 마법을 그리는 것 —

| **룬** | 무엇으로 때리는가 | **속성** — 원소 · 상태이상 |
| **문양** | 어떻게 나가는가 | **방식** — 방향 · 기점 · 발수 · 궤적 |

### 종이 확대 (돋보기) — 작은 문양을 정밀하게 (사용자 요청)

**휠 = 확대(×1~×4) · 휠클릭 드래그 = 종이 밀기.** `src/drawing/drawing_canvas.gd`.

- **확대는 보는 배율만 바꾼다.** 저장되는 획은 언제나 종이 정규 좌표(0..1) — **인식·잉크·발사는
  배율을 모른다.** 화면↔종이 좌표를 넘는 지점은 `_to_paper()` 하나뿐이다
- 획(Line2D)을 `_ink_layer`(Node2D)에 모으고 거기에 zoom·pan을 건다 → 획·방위 가이드·본보기가
  함께 확대되고, 캔버스가 `clip_contents`라 넘치는 부분은 자동으로 잘린다
- **커서 아래 종이 점을 붙잡고 확대**한다 (보던 자리가 달아나지 않는다) · pan은 종이가 뷰를 덮는
  범위로 갇힌다 (종이 밖 허공 차단) · **긋는 도중에는 휠 무시** (그리다 종이가 움직이면 획이 망가진다)
- 필압은 **화면 픽셀 속도**로 잰다 — 손 속도는 확대해도 안 변하니까. 종이 좌표로 재면 확대할수록 굵어진다
- 점 최소 간격은 확대에 반비례(`MIN_PX_DIST / _zoom`) — 확대의 목적이 정밀도인데 여기서 뭉개면 무의미
- **검증 13건 신규** (`test_drawing_canvas_auto`, 33/33): 내부 API가 아니라 **실제 마우스 이벤트**를
  주입해 "×2로 확대해 그린 획 = 원래 획(정규 좌표 오차 <0.02)"을 못 박았다

1. **제작 UI = 좌우로 펼친 책** — 왼쪽 종이(그린다) / 오른쪽 도안 책자(본다). **ESC 토글 오버레이**이고
   씬 전환이 아니다. 작업대에 다가가 E로 연다 — 덮으면 세계가 그대로 있어 **그려서 바로 쏜다**
2. **오른쪽 탭은 참조 전용** — 진·룬·문양 탭에서 무엇을 보든 캔버스는 달라지지 않는다.
   골라 찍는 게 아니라 **보고 따라 그린다.** 입력은 끝까지 손그림 하나뿐, 판정은 인식기가 한다
3. **아트는 당분간 손대지 않는다** — "추후 디자인 셋업"으로 미룸. 해상도(640×360)도 유지.
   ⚠ **아트 작업을 새로 시작하지 말 것** (사용자 명시)

### 아트 현황 — 조사만 하고 보류 (사용자 지시)

사용자 지적: "픽셀도 뭣도 아닌 느낌 · 표현력을 올리고 싶다". 실측 결과:

- **640×360은 프레임버퍼가 아니라 레이아웃 좌표계다.** `stretch/mode="canvas_items"` 덕분에
  **먹선·글씨는 이미 네이티브 해상도(2560×1440)로 렌더된다.** 4배 확대되는 건 픽셀 에셋뿐이다
- 그래서 "픽셀도 뭣도 아닌" 정체 = **고해상도 벡터 먹선 + 4배 확대 Nearest 픽셀아트가 한 화면 공존**
- 픽셀 에셋 총량: **PNG 30개 / 약 145~151 프레임** (aseprite 원본 30개 전부 보존됨).
  코드 배선은 시트 규격 상수 8곳(`TILE_PX`·`frame_size`)만 바꾸면 끝 — 구조 변경 불필요
- **표현력 부족의 진짜 원인은 밀도가 아니다**: 보스 gale이 64×64 = 캐릭터의 2배·화면 폭 10%뿐이다.
  코어 키퍼류의 웅장함은 **보스를 캐릭터의 4~8배로 그려서** 나온다 — 해상도와 무관.
  참고: 스타듀는 캐릭터가 16×32(우리보다 낮다), 데드셀은 32~128px "모던 HD 픽셀아트"
- 해상도별 정수 배율: **640×360만 FHD(3배)·1440p(4배) 둘 다 정확.** 밀도를 올리면 정수 배율이 깨진다

### 🔴 이번 세션에 잡은 **실제 버그** 3건 (전부 테스트가 초록인 채로 숨어 있었다)

1. **모든 문양이 90도 틀어져 나갔다** (세션 7 최후반 발견 — 사용자가 의심해서 잡혔다)
   `design_builder`는 방향을 **상대각**(그린각 − aim_axis)으로 저장하는데 `spell_system`은 **절대각**으로
   알고 다시 `(에임 − aim_axis)`만큼 회전 → **aim_axis가 두 번 빠졌다.** 앞으로 그은 문양이 옆으로 날아갔다.
   → 방향도 **캔버스 절대각**으로 통일 (strokes·origin과 같은 좌표계, 발사 때 **한 번만** 회전)
   - **왜 273건이 초록이었나**: 테스트가 `ArrowData.direction`이라는 **중간 표현**만 봤다. 두 모듈의
     계약이 어긋났는데 각자의 테스트는 각자 옳았다. → **실제 발사각(`_world_angle`)으로 검증**하도록 재작성
2. **불△(삼각형)이 인식되지 않았다** — 시작 룬이자 튜토리얼 첫 글자인데 안 그려졌다.
   닫힌 삼각형의 감김은 이론상 1.0바퀴지만 **마지막 꼭짓점의 꺾임이 계산에 안 잡혀** 0.67로 내려앉는다.
   `WINDING_FIRE_MIN=0.55` 게이트가 불△를 **후보에서 통째로 지웠다**.
   실측 분포로 확인: **불△(0.16–0.90)는 충격>·물~과 완전히 겹쳐 — 가르는 문턱이 존재하지 않는다.**
   → 감김을 **스무딩 후** 측정 + **하드 게이트를 바람◎에만** 남기고, 피처는 "$1이 확신 못 할 때만 개입하는
   보조 신호"로 강등. **전체 인식률 96.7% → 99.5%** (물/바람 교차 0 유지)
3. **충격>가 물~로 11.3% 오인** — 위 조사 중 발견된 **기존 약점**. 원인이 같았다(타이브레이크가 정답 삭제)

**교훈**: 기존 룬 테스트는 **깨끗한 합성 도형**만 썼다 — 작고 지터 있는 손그림을 전혀 건드리지 않았다.
손그림 스트레스 테스트(4종 × 40, 크기·회전·노이즈 무작위)를 신설했다.

### 세션 9 말미 — 사용자 정정 2건 (**구현 완료**, 전 스위트 그린)

**1. "전원 1획"은 설계가 아니었다.** `$1`(유니스트로크)을 고른 데서 **딸려온 제약**인데 GDD §4.2에
*기획 스펙*처럼 적혀 있었다 (**리드가 제약을 의도로 착각**). **획 수에 제한을 두지 않는다.**
→ GDD에서 제거하고, `$P` 교체가 이 제약을 없애는 작업임을 명시

**2. 잉크 = 통에서 실제로 나온 양** (사용자 확정). "획"이라는 추상 단위가 아니다.
- **`∫ 굵기 ds`** — 구간 길이 × 그 구간의 붓 굵기. 꾹 눌러 굵게 그으면 실제로 더 쓴다.
  ~~평균 필압 × 전체 길이~~ 는 **어디서 눌렀는지를 뭉개서** 실제 사용량이 아니었다
- 🔴 **진 크기 할증(최대 3배) 폐기 — 이중 과금이었다.** 큰 진은 **둘레가 길어서 이미** 잉크를 더 먹는다
  (반지름 2배 → 둘레 2배 → 잉크 2배). 할증은 그 위에 또 물린 것이다
- 🔴 **잉크가 숫자 하나가 됐다.** v1.7까지 **두 개**였다 — 종이 상한 판정은 물리량으로, 제작 비용은
  할증 붙은 값으로 재고 있었다. **같은 이름의 다른 숫자 둘.** 이제 `stroke_ink_units()` 하나가
  양쪽에 쓰인다 (`balance.circle_radius_ink_mult`·`aimed_circle_ink_mult`는 **폐기 표시 후 미사용**)
- **테스트 전제도 뒤집혔다**: 세션 7의 *"필압은 잉크에 중립"* 은 **평균으로 뭉갠 데서 나온 착시**였다.
  이제 필압이 잉크에 **실제로 반영된다**(그게 요점). 대신 **계통적 인플레가 없음**(편차 <5%)을 검증한다

### 2순위 — 아트 "자글자글" 전면 재조정 (플레이 검증 후)

사용자 지적(세션 5): 전체화면에서 **바닥뿐 아니라 UI·캐릭터까지 전반적으로** 자글거린다.

- **스케일링은 무죄** — 메인 모니터 2560×1440 ÷ 뷰포트 640×360 = 정확히 4배 정수 배율. 픽셀은 균일하게 커진다
  (`display/window/stretch/mode="viewport"`, filter Nearest). 즉 렌더 설정이 아니라 **에셋 자체가 원인**
- **원인: 고립된 1픽셀 고대비 노이즈** ("소금후추"). 타일셋 실측 — 풀 기본 10/256px·명도차 37.7 /
  풀 변형 11/256·명도차 75.9 / 보스존 바닥 25/256. 4배 확대 시 각 점이 4×4 덩어리가 되고 바닥 4,836장이
  깔려 화면 전체가 자글거림. x8 단일 타일 검수로는 못 잡는 실수 — **화면 전체 기준으로 검수할 것**
- 같은 원인이 UI·캐릭터·적에도 있을 가능성이 높다 (전부 같은 방식으로 그렸음). **전 에셋 노이즈 감사 필요**
- 미관 문제만이 아니라 **전투 가독성 저하** — 바닥이 시끄러우면 적·플레이어가 배경에 묻힘 (ART_SPEC P2 목표와 충돌)
- 방향 후보: (a) 바닥 거의 평탄 + 디테일은 술·들꽃 타일에 집중 (b) 점 개수 유지하되 명도차 38~76 → 12로 저대비화
  (c) 완전 평탄. **미결 — 사용자 확인 필요**
