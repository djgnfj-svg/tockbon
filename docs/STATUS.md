## 세션 26 (2026-07-17) — **숲 원정: 그린 마법이 쓸 데가 생겼다**

### ✅ 저장이 돈다 (F3 — 사용자 확정: *"켜면 이어서 한다"*)

**세션 21 대청소가 부팅 흐름을 지우면서 `load_game()`을 부르는 사람이 아무도 안 남았다** →
`_ready_to_save`가 영원히 false → `save_game()`이 **전부 조용히 return** → **껐다 켜면 그린
마법진이 통째로 사라졌다.** 에러도 경고도 없었다(세이브가 아예 안 만들어지니 로드가 실패할
일도 없다). → `SaveManager._ready` → `load_game()` **한 줄**. 오토로드 마지막이라 GameState·
Clock·Db가 이미 서 있고, **부팅에 딱 한 번** 돈다(씬에서 부르면 귀환할 때마다 그 판을 날린다).

🔴 **`test_save_auto`가 이 버그를 두 세션 동안 못 잡은 이유 — 테스트가 스스로 `load_game()`을
불러 `_ready_to_save`를 켜 줬다.** 게임은 아무도 안 부르는데 테스트만 불러 준 셈이라 이후의
저장 검증이 전부 **거짓 초록불**이었다. → 회귀 확인을 **`load_game()` 호출 전에** 넣었다
(순서가 곧 검출력이다. 뮤테이션으로 1건 검출 확인).

### 🔴🔴 순환 preload — 귀환해도 베이스로 못 돌아갔다 (실제 게임에서만 드러남)

`base.gd`가 `forest.tscn`을, `forest.gd`가 `base.tscn`을 **서로 preload**했다(리드가 세션 22 M1의
`forge_scene` 선례를 잘못 확장했다 — 책은 base를 안 무니 순환이 아니었는데). 베이스로 부팅하면
base.tscn이 **아직 로드 중**일 때 forest.gd가 그걸 preload해 `base_scene`이 **노드 0개 껍데기**로
굳는다 → 숲에서 [E]를 눌러도 `Parameter "new_scene" is null`. 실측: 껍데기 0개 vs 직접 load 22개.

🔴 **헤드리스는 절대 못 잡는다** — `test_forest_auto`는 forest.tscn을 **먼저** 로드하므로 base
preload가 멀쩡히 끝난다. **베이스로 부팅한 실제 게임에서만** 깨진다. 전 스위트 그린이었다.
→ `@export_file` 경로 + `change_scene_to_file`. **경로 문자열엔 로드 시점이 없어 순환이 성립하지
않는다.** (백로그가 원래 `change_scene_to_file`이라 적어 뒀는데 리드가 PackedScene으로 과하게 만들었다.)

**전체 루프를 실제 게임에서 왕복 검증**: 맺기 → 숲길 [E] → 숲 → 귀환 [E] → 베이스 → 저장 →

## 세션 25 (2026-07-17) — **사용자가 직접 그려 보니 다 어긋나 있었다**

> 세션 24까지 리드는 "그리는 재미"를 시뮬레이션으로 검증해 왔다. 사용자가 **마우스로 직접
> 그려 보자** 한 시간 만에 8건이 나왔다. 그중 둘은 **기능이 통째로 죽어 있었다.**

### 🔴 정체성 확정 — 조립 모드를 만들었다가 **폐기했다**

사용자가 *"보기를 누르면 자동으로 마법진에 적용되는 조립 느낌"*을 보고 싶다 해서 만들고
손그림과 나란히 견줬다(T키 토글). 결론은 **한 커밋 만에 폐기**: *"잉크를 선택해서 그리는 게
더 재미있긴하겠다 이거 패기 ㅇㅇ 이 조립하는거"*.
→ **[[takbon-hand-trace-commit]]의 탁본 정체성이 유지된다.** 조립이 이겼으면 점수·펑·펜·등급이
전부 놀게 돼 다른 재미 축을 새로 세워야 했다. 남기지 않은 이유: 비교가 끝난 축을 남기면
"언젠가 쓸지도"로 썩는다(세션 21 대청소가 치운 게 그런 코드였다).

### 손그림이 실제로는 **그릴 수가 없었다** — 넷 다 "보이는 것과 그리는 것이 어긋남"

| 사용자 말 | 실체 |
|---|---|
| *"획단위로 초기화되서 화살표를 그리가가 어렵네?"* | 누를 때마다 `begin_stroke`가 문지름을 **통째로 지웠다** → 한 조각 = 한 획 강제. 선 긋고 펜 떼서 화살촉을 그리면 선이 사라져 **화살표가 물리적으로 불가능**했다. → 먹선을 **획 목록**으로(이어 붙이면 화살표가 삼각형이 된다) · 우클릭 = 다시 그리기 |
| *"문양을 선택했을때 밑그림이 그려져야지"* | 문양 밑그림이 **방향 없는 작대기**였다. `GlyphDef.inward`를 **아무도 안 읽어** 응집·발산 밑그림이 동일 → Q·W를 눌러도 바뀔 게 없었다. 책 셀은 화살표인데 판은 작대기 |
| *"8방 했을때 이미 주황색으로 선택되어있어"* | `_refresh_trace`가 첫 빈 칸을 멋대로 잡았다 → 칸은 **사용자가 클릭해서** 고른다 (채우는 순서도 사용자 것) |
| *"문양 모양도 그냥 문양 하나만"* | 셀 아이콘이 **8방향 다발** → 셀이 옆 탭의 **문양본**처럼 읽혔다. 화살표 하나로 |

### 🔴 화살촉이 **붓보다 작았다** (사용자: *"한 획만 검증하니? 여러획쓸꺼같아서 화살표는"*)

말이 맞았지만 **원인은 "한 획만 검증"이 아니었다 — 화살촉을 그릴 이유가 없었다.** 실측:
문양 반길이 14px인데 **붓의 드러남 반경이 9.4px**라, 화살촉 점 전체가 몸통 끝에서 최대 8.6px —
**몸통을 긋는 순간 화살촉이 통째로 드러났다.** 화살표 하나가 붓 한 자국 크기였다.
→ 크기 0.12→**0.17** · 깃 벌어짐 0.34→**0.62**(12.4px > 9.4px). 실측 **몸통만 0.76 → 화살촉까지 1.00**.
🔴 이 셋은 결국 `REVEAL_RADIUS_FRAC`(붓)과의 **비율**이 전부다 — 근거를 상수 주석에 적었다.

### 🔴🔴 발사가 통째로 죽어 있었다 — 그리고 **리드가 사용자에게 틀리게 말했다**

사용자: *"맽기까지는 되는데 안쏴지네"* → *"아무것도 안나감"* → ***"좌클릭이 안먹나?"* (맞혔다)**

원인: `Ground`(화면을 다 덮는 ColorRect)의 `mouse_filter`가 **기본값 STOP** → 바닥이 좌클릭을
전부 먹어 `_unhandled_input`에 안 왔다 → `_fire()`가 **아예 안 불렸다**. 에러도 경고도 없다
(세션 24 「총구 자살」과 같은 침묵). → `mouse_filter = 2`. 실측 **0회 → 1회**.

**리드는 "발사는 정상"이라고 여러 번 틀리게 말했다.** 재현이 전부 `_fire()` **직접 호출**·
`attack_basic` **액션 주입**이라 **Control 계층을 건너뛰었다** — 전 스위트 그린인데 게임에선
아무것도 안 나갔다. 사용자가 계속 "안 된다"고 했는데 리드가 자기 초록불을 믿고 딴 데를 팠다.
🔴 **`push_input` 테스트를 새로 써도 헤드리스에선 통과한다**(검출력 0 — 렌더가 없어 Control
히트 테스트가 실제와 다르다). **에디터 실제 게임에서만 재현된다.**
→ CLAUDE.md 검증 절 + memory `godot-headless-cannot-test-clicks`에 못 박았다.

- **[맺기 (분석)] 버튼은 아무것도 안 맺었다** (분석 리포트만 띄운다. 맺는 건 [마력 주입]).

  idx별로 다른 모양을 그리기. 호출부·규약·테스트는 그대로다

## 세션 24 (2026-07-17) — **등급이 기준선과 하나가 됐다**

> 사용자: *"지금 조금 뭔가 어긋남부터 일단 수정을 해야 될 듯 / 65~75가 무난, 75~85가 평타,
> 85~95가 괜찮은, 95~100이 완벽 (…) 백은 뭔가 달랐으면 좋겠네. 백은 퍼펙트라면서? /
> 손맛보단 그거부터 맞춰줘"* → 세션 23이 남긴 「⚠ 남은 어긋남」을 닫았다.

**무엇이 어긋나 있었나:** 등급은 점수가 **아무것도 안 하던 시절**의 숫자(55/75)를 채점기가
따로 쥐고 있었다. 세션 23이 펑 기준선 0.65를 들여오면서 「무난」(55~75)이 그 선을 **걸쳤다** —
같은 "무난"이 61점이면 터지고 70점이면 견뎠다. 등급이 거짓말을 한 게 아니라 **두 개의 진실**이
있었던 것이다.

**새 구간 (사용자 확정):** 65 이하 **사용 불가** · 65~75 **무난** · 75~85 **평타** ·
85~95 **괜찮음** · 95~100 **완벽** · 100 **퍼펙트**.

**🔴 구조 — 등급을 `trace_scorer` → `src/core/ring_power.gd`로 옮겼다.** 최하단이 곧 펑
기준선이기 때문이다. 등급이 65를 자기 상수로 베껴 적으면 **balance만 바꿨을 때 조용히
갈라진다** — 방금 고친 어긋남이 그대로 재발한다. 그래서 `grade_of`는 숫자를 안 보고
**`is_stable()`을 그대로 부른다**: 두 경계는 한 값이지 두 값이 아니다.
(채점기 = "얼마나 잘 그렸나"만 잰다. "그래서 쓸 수 있나"는 다른 관심사다.)

**「퍼펙트」는 표시 반올림과 묶었다** (`ring_grade_perfect = 0.995`): 리포트가 `round(점수×100)`을
찍으므로 이 값이 곧 *"화면에 100으로 뜨는 순간"*이다(사용자 확정). 0.999로 올리면 **100점이라
적어 놓고 「완벽」**이라는 새 어긋남이 생긴다 — 테스트가 이 성질을 훑어서 못 박는다.
UI는 `is_perfect()`로 금색 배경 + ★를 준다 — **이름을 `==`로 비교하지 않는다**(이름이 바뀌면
조용히 평범해진다).

**⚠ 규칙 하나가 완화됐다:** 등급이 주입 **전에** 보이므로 이제 **펑 여부를 미리 알려 준다.**
세션 23의 「주입 전 안내 금지」와 정면으로 부딪혀 물어봤고, 사용자가 *"등급이 알려 줘도 됨"*으로
확정했다. 금지는 **명시 문구**와 **위력 곡선의 평평한 구간**에만 남는다(곡선이 지수인 이유는 그대로).

**🔴 새로 배운 함정 — GDScript가 `const BAL.프로퍼티`를 컴파일 타임에 굳힌다.** "기준선을
0.80으로 올리면 등급도 따라온다"를 테스트로 짰는데 **실패**했다. 파 보니 `RP.BAL.ring_stability_min`은
