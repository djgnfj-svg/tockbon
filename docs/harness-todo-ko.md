## 1. 빌드를 병렬로 — **사용자 요청 (2026-08-16)**

> *"이거 빌드될 때 병렬로 할 수 있게 하는 방법 없나? 개발 한번 할 때마다 너무 시간이 오래 잡아먹혀서."*

### 지금 무엇이 직렬인가

`build-feature` 스킬이 다섯 에이전트를 **순서대로** 돌린다 — spec → builder → verify-run · verify-look ·
verify-read. **직렬인 데는 이유가 있는 것과 없는 것이 섞여 있다**:

| 단계 | 직렬이어야 하나 | 왜 |
|---|---|---|
| spec → builder | **그렇다** | 계획 없이 못 짓는다 |
| builder → verify | **그렇다** | 지어지지 않은 것은 검증할 수 없다 |
| verify 셋끼리 | **아니다** | 서로 안 읽는다. **지금도 병렬로 돌릴 수 있다** |
| builder 여러 개 | **조건부** | 슬라이스가 독립이면 가능. 아래를 볼 것 |

**네트 라운드는 이미 병렬이다** — 네트마다 자기 프로세스이고, 속도가 아니라 **정직함** 때문이다
(사면이 자기 네트 안에 갇힌다). **이 성질은 깨지 말 것.**

### 병렬 builder의 진짜 장벽 — 트리가 하나뿐이라는 것

같은 트리에서 두 builder가 동시에 편집하면 **측정이 무효가 된다.** 레포가 이미 그걸 두 가지 방법으로
잡아내고 있다: `[race]`(라운드 *도중*의 편집)와 `[지문]`(라운드 *사이*의 편집). 다섯 에이전트가 한 트리를
공유했던 밤에 뮤테이션 검증자의 편집이 조용히 되돌려졌고, 라운드 둘이 남의 편집으로 오염됐다.

⇒ **답은 worktree 격리이고, 레포에 이미 그 습관이 있다.** 다만 값이 붙는다:

- **새 worktree에는 `.godot` 임포트 캐시가 없어서 모든 네트가 빨간불이 된다** — 코드 실패가 아니다.
  `--headless --path <root> --import`를 먼저 돌려야 한다. 하룻밤에 네 에이전트가 여기 걸렸다
- **자동 정리가 거의 안 된다.** 하룻밤 700MB, 측정치다. `git worktree remove --force` + `prune`
- **worktree는 분기한 커밋에서 얼어붙는다.** 시작 직전에 `main`에서 다시 분기할 것 — 두 에이전트가
  그날의 다른 변경을 모르는 베이스 위에 한 세션치를 지은 적이 있다

### 그래서 할 일

1. **verify 셋을 한 메시지에서 동시에 띄운다.** 오늘 당장 되고 값이 0이다. `build-feature`를 그렇게 고칠 것
2. **spec이 「슬라이스가 독립인가」를 표로 내게 한다.** 파일이 안 겹치는 슬라이스가 둘 이상이면
   builder를 worktree마다 하나씩. 겹치면 직렬 — **판단을 builder가 아니라 spec이 한다**
3. **worktree 왕복을 스킬이 직접 처리한다** — 분기 · `--import` · 병합 · `remove --force` + `prune`.
   손으로 하면 위 셋 중 하나를 반드시 빠뜨린다
4. ⚠ **병합은 여전히 직렬이다.** 두 builder가 `look.gd` 같은 한 파일 규칙 파일을 동시에 건드리면
   반드시 충돌한다. **한 파일 규칙과 병렬 빌드는 서로 싸운다** — 슬라이스를 나눌 때 이걸 먼저 볼 것

⚠ **그리고 병렬이 항상 빠른 것은 아니다.** 슬라이스 셋 중 하나가 나머지의 세 배 걸리면 벽시계는
그 하나이고, worktree 설치·임포트·병합 값만 더 든다. **먼저 재고 나서 병렬화할 것** —
어느 단계가 실제로 오래 걸리는지 지금 아무도 모른다.

### 아직 안 정한 것

- **한 판에 builder 몇 개까지.** 에이전트마다 worktree 하나이고 디스크가 실제 제약이다
- **verify를 슬라이스마다 돌릴지, 병합 후 한 번 돌릴지.** 전자는 빠르고 후자만이 통합을 본다
