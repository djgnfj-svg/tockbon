# 던전 구조 설계 — 「열린 맵 · 지점을 밟고 · 살아 나온다」

> **세99 사용자 확정.** 발단 = *"메인 루프를 만들어서 이제는 루프 테스트를 하면서 디테일을 잡아볼 생각이야.
> 이번주 목표는 깔끔 1루프를 만드는거임"* → *"던전 구조부터 잡자"*.
>
> 🔴🔴 **이 설계가 존재하는 진짜 이유** — 사용자 원문: *"내가 생각하는 구현이 아니라 AI가 대략적으로 구현해 놓은
> 상태여서 수정 필요"*. 지금 던전은 **기획 없이 얹힌 얼개**다. 그래서 이 문서는 「기능 추가」가 아니라
> **「무대의 정체를 처음으로 정하는 것」**이다.
>
> 관련 정본: `docs/GDD.md` §6(익스트랙션) · `docs/PROGRESSION.md`(관문) · `docs/BACKLOG.md`.

## 2. 데이터 스키마 — 「새 X = .tres 한 장」을 지킨다

🔴 **원칙**: 기존 필드는 **의미를 안 바꾼다.** 새 필드는 전부 **비어 있으면 지금 동작**이다.

🔴🔴 **단, 그건 「데이터 축」에만 참이다**(세99 architect 리뷰가 이 문서의 초안 주장을 반박했다).
초안은 *"회귀가 구조적으로 0"*이라고 적었는데 **코드·그물에는 거짓**이다 —
필드를 **비워 두면** 아무 일도 안 나지만, **실제로 채우는 순간** 기존 계약과 기존 그물이 깨지는 자리가 넷 있고
그중 둘은 **에러가 0**이다(→ §6의 S9·S10·S11·S12).
**「되돌리기가 싸다」와 「켜는 게 안전하다」는 다른 말이다.**

### 2-1. `MobSpawn` — 좌표 고정, 정체는 굴림

```
enemy_id     : StringName   (기존) 🔴 값이 있으면 지금 그대로 — 회귀 0
position     : Vector2      (기존)
pool_tag     : StringName   (신설) 비면 기존 동작. 값이 있으면 ChapterDef.mob_pool에서 굴려 뽑는다
```

**왜 좌표는 고정인가** — 사용자 확정 *"지형은 동일하고 나오는 몬스터들이 랜덤"*.
스폰 자리는 지형이 정하는 것(길목·빈터)이라 사람이 놓는 게 맞고, **바뀌는 건 「거기 뭐가 서 있나」**다.

### 2-2. `ChapterDef` — 풀과 네임드가 붙는다

```
(기존 전부 유지: id · order · title · boss_enemy_id · boss_scene_path · boss_spawn ·
 room_ground_color · mob_spawns · reward_unlock)

room_scene_path : String              (신설) 비면 boss_room.tscn — 🔴 D8의 착지점
mob_pool        : Array[MobWeight]    (신설) 비면 랜덤 없음(지금 동작)
named_pool      : Array[NamedSpawn]   (신설) 비면 네임드 없음
landmarks       : Array[LandmarkSlot] (신설) 비면 지점 없음
extract_points  : Array[Vector2]      (신설) 비면 남쪽 출구 하나(지금 동작)
```

### 2-3. 신설 스키마 넷

```
MobWeight        enemy_id · weight(int) · pool_tag
                 → 「이 챕터의 잡몹 풀」. weight 비례로 뽑는다

NamedSpawn       enemy_id · chance(0~1) · at_landmark(StringName, 비면 자유 위치) · position
                 → 매 판 각각 굴린다. 🔴 서로 독립 — 「하나도 안 뜸」이 정상 결과다

LandmarkSlot     landmark_id · position
                 → 맵의 어느 자리에 어떤 지점이 서나 (위치 고정)

LandmarkDef      id · kind(RUIN/NEST/ALTAR) · scene_path · 종류별 params
                 → data/landmarks/*.tres. 🔴 「새 지점 = .tres 한 장 + 프롭 씬 한 장」
```

### 2-4. `InteractZone` — 홀드를 얹는다 (공용이라 조심)

```
hold_sec : float = 0.0   (신설) 🔴 0이면 지금 그대로 즉시 — 마을의 책상·문은 한 톨도 안 바뀐다
```

🔴 **값의 소유자는 `balance`다 — `hold_sec`은 「0이냐 아니냐」 스위치로만 써라.**
출구가 여럿이면 씬마다 한 벌이 생겨 **튜닝할 값이 흩어진다**(§8이 이 값을 F5 미결로 남겼으므로 반드시 한 곳이어야 한다).
⚠ 실측: **`data/balance.tres`는 값이 한 줄도 안 적힌 껍데기**이고 전부 `balance_data.gd`의 `@export` 기본값으로 돈다
— 즉 「balance에 넣는다」의 실제 작업은 **스키마에 `@export` 한 줄**이고 그건 **core = 리드 몫**이다.

🔴 **홀드는 폴링(`_process`)으로 짜라 — 「뗐나」를 이벤트로 받지 마라.**
`player_caster._tick_cast` 머리말이 **실측 세 가지**를 적어 뒀고 전부 에러가 0이다:
① 화면 덮는 Control이 `mouse_filter=STOP`이면 뗀 이벤트를 먹는다 ② 창 포커스가 빠지면 엔진이 액션만 풀고 이벤트를 안 쏜다(alt-tab)
③ `_unhandled_input`은 모달 중 아예 안 온다. **같은 함정이 [E] 홀드에 그대로 재현된다.**
✅ 덤으로 `_process` 카운트다운은 **씬 전환에 구조적으로 안전하다**(노드와 함께 죽는다 — `SceneTreeTimer`엔 그 보장이 없다).

**취소 트리거는 넷이다**(초안은 피격 하나만 적었다):
① 피격(`EventBus.player_hurt`) ② **범위 이탈**(`_on_body_exited`) ③ **모달 열림**(`GameState.ui_modal_open`) ④ 씬 전환(위 ✅로 자동).

⚠ **홀드 진행을 화면에 어떻게 보이나의 담당이 없다** — §1 다이어그램의 `███░░`는 새 물건이다.
**dev(진행 상태) + vfx(보이는 채우기)** 로 나눈다.

🔴 **`InteractZone`은 마을·보스방이 같이 쓰는 공용 배우**라 기본값이 곧 회귀 방어선이다.
피격 시 취소는 `EventBus`의 플레이어 피격 신호를 홀드 중에만 구독해 푼다(상시 구독 금지).

⚠ **`zone_id = &"exit"`와 `&"portal"`을 갈라 둔 게 계약이다** — 포탈은 보스 처치 후에만 뜨고(**매번 다시 뜬다**) 출구는 처음부터 있다.
탈출구를 여럿으로 늘려도 **전부 `&"exit"`**여야 `test_chapter_auto`의 포탈 그물이 안 빨개진다.

✅ **이중 전환 방어는 이미 서 있다** — 출구와 포탈이 같은 `_extract`로 묶여 있고 `_leaving` 가드가 두 번 나가는 걸 막는다.
**탈출구를 여럿으로 늘려도 이 가드가 그대로 커버한다**(새로 짜지 마라 — 세47 「이미 있는 배선」의 결).

## 3. 지점 셋 — 무엇이 다른가

🔴 **셋의 차이는 「보상 크기」가 아니라 「무슨 일이 일어나나」다.** 크기만 다르면 D4를 고른 의미가 없다.

| | 🏚 **폐허** | 🪦 **둥지** | 🪵 **제단** |
|---|---|---|---|
| **도착하면** | 전투 없음 · 걸린 상자 | 몹이 계속 기어나온다 | 조용하다 |
| **여는 값** | 열면 **소리가 나 몹이 몰려온다** | **핵(알)을 깨야** 멈춘다 | **마법을 바친다**(마나 소모) |
| **안 할 수 있나** | ✅ 지나가도 된다 | ✅ 지나가도 된다 | ✅ 지나가도 된다 |
| **주는 것** | 재료 · coin 뭉치 | 재료 **다량** | **상위 재료 · 소모품** — 🔴 **진행에 걸린 것은 안 준다** |
| **성격** | *"열고 버틸 자신 있나"* | *"들어가서 핵까지 닿을 수 있나"* | *"마나를 여기 쓸까 보스에 쓸까"* |

🔴🔴 **「도착하면·여는 값」의 조작과 산출은 세100에 확정됐다 — §10을 같이 읽어라.**
**셋 공통으로 [E] 한 번에 열리고**(D10 · 홀드가 아니다) **판당 한 번뿐이며**(D11) 위 표의 「여는 값」은 그 위에 얹는 층이다.
⚠ **둥지의 「몹이 계속 기어나온다 / 핵을 깨야 멈춘다」는 각하됐다**(D10·D11 — 세99 사용자 *"그냥 간단한데"*의 착지점).
이 표에서 살아 있는 건 **「셋이 서로 다른 일이 일어난다」(D4)는 성격 축**이다.

### ✅ 첫 랜드마크 = **늑대 둥지** (세99 사용자 확정)

사용자 원문: *"그냥 간단한데 그냥 짐승들 둥지 있는거임 확산된 늑대하면서 많은 늑대들이 있을듯"*.
→ **NEST 하나만 먼저 세운다.** 🔴 *"간단한데"*를 따라 **장치(무한 스폰·핵 깨기)는 안 넣는다** —
지금 필요한 건 **눈에 보이는 목적지 + 그 주변에 퍼져 있는 늑대 무리**다.
아트는 세99에 완성됐다(`nest_wolf.png` 온전함 / `nest_wolf_broken.png` 비워짐 · 화면 키 178×121).
⚠ **폐허·제단은 아직 그림이 없다** — §3 표의 나머지 둘은 설계로만 서 있다.

🎯 **이 랜드마크의 목적 = 「입구에서 흙길이 여기로 이어진다」**(사용자가 말한 이번 목표).
그전까지 길은 **가장자리에서 튀어나온 토막**이라 끝이 허공에서 끊겼다 — **목적지가 생겨야 동선이 된다.**

### 🔴 소유권 둘을 설계가 정해 준다 (구현자가 고르면 갈린다)

**ⓐ 적을 누가 스폰하나 — 「둥지」가 아니라 방이 한다.**
지금 리포의 preload 방향은 **field → props 단방향**이다(`forest_enemy`가 `drop_pickup`을, `boss_room`이 `portal`을 문다).
지점을 `src/props/`에 두고 거기서 `forest_enemy.tscn`을 물면 **그 방향이 처음으로 뒤집힌다**(takbon-rules §0 위반).
→ 🔴 **지점은 겉모습·판정만 지고, 「지금 하나 내보내라」를 부모에게 알린다. 스폰은 `boss_room`이 한다**
(이미 유일한 스폰 소유자다 — `_spawn_boss`·`_spawn_mobs`). **부모가 자식 시그널을 잇는 조합 루트라 EventBus 신설이 0**이고,
S1(스폰 수를 세는 그물)이 **한 자리에서** 성립한다.

**ⓑ 보상은 새 드롭 기계를 만들지 않는다.**
드롭 굴림·낱개 스폰은 `forest_enemy`의 `_roll_drops`/`_spawn_loose` **한 곳뿐**이고 둘 다 private다.
지점이 자기 로직을 새로 쓰면 `DropEntry`의 **배타 짝 규칙 셋**이 두 벌이 된다(takbon-rules §5-1이 「조용히 깨진다」로 못 박은 자리).
→ 🔴 **지점 보상도 `DropEntry` 배열을 쓰고, 굴림·스폰을 field 안 공용 함수로 한 번 올려** 적과 지점이 같은 것을 부르게 한다.
✅ **해금은 더 간단하다 — `EventBus.codex_unlocked` 한 발**이면 끝이다(발신처가 이미 넷).

⚠ **`until_unlock`을 지점과 같이 켜지 마라** — `DropEntry.unlock_id`와 병용하면 `if…elif` 때문에
**`chance`를 통째로 안 봐서 모든 잡몹이 확정 드롭**이 된다(takbon-rules §5-1).

### 🔴🔴 제단은 문양-고리를 주지 않는다 (세99 사용자 확정 — 초안을 각하했다)

**초안은 제단을 「문양-고리(상위)를 주는 자리」로 뒀다가 각하됐다.** 이유가 이 설계 안의 자기모순이었기 때문이다:

- 문양-고리는 **엔딩 조건(문양 전종 회수)의 유일한 통로**다 = 사실상 **진행 보상**이다.
- 그런데 제단은 **매 판 굴러가는 물건**이다.
- → **D6가 막으려던 바로 그 상태**(*"언제 어떻게 얻을지 설계를 못 하니까 불안하다"* — 세57 사용자 원문)가 된다.

🔴 **확정: 제단은 「있으면 좋은 것」만 준다** — 상위 재료·coin·소모품.
**문양-고리는 확정 경로로만 나간다**: 보스 드롭 · 공방 제작 · 퀘스트 턴인.

⚠ **그래서 「문양 9종 중 4종(`pierce`·`homing`·`bounce`·`thrust`)에 획득 경로가 없다」는 이 설계가 안 푼다**(→ §5).
실측: 통로가 문양-고리뿐인데 `data/glyph_rings/` 5장이 쓰는 motif가 `0·1·6·7·8`뿐이라 **엔딩 조건의 44%가 도달 불가**다.
🔴 **별건으로 푸는 게 오히려 확실하다** — 공방 레시피 `.tres` 몇 장이면 확정 경로가 서고, 그게 D6와도 맞는다.

## 4. 네임드 — 「오늘 뭔가 있다」

- 매 판 입장 시 `named_pool`의 각 항목을 **독립적으로** 굴린다. **하나도 안 뜨는 게 정상 결과**다.
- 뜨면 지정 지점(`at_landmark`) 또는 자유 위치에 선다.
- 🔴 **표시 = 생김새다. 빛나게 하지 마라**(세99 사용자 확정 — *"눈으로 봤을때 차이가 있는데 몸에서 빛이나는거 까진 별로임"*).
  **덩치·색·실루엣**으로 구별한다 — 화면에 들어오는 순간 *"저건 다르다"*가 읽히면 된다.
  ⚠ **화면 밖 표시(오라·HUD 화살표·입장 알림)는 안 만든다** — 각하됐다.
  ✅ **`EnemyDef.params` 한 장으로 성립한다**: `size`·**`tint`**·`sprite`·`anim_fps`가 `_apply_look`/`_setup_frames`를 지난다.
  🔴🔴 **`params.color`가 아니다 — 초안이 틀렸고 세99 구현이 실측으로 반박했다.**
  `color`는 **세45에 스프라이트로 갈아타며 `_visual.color`가 사라져** 지금은 **죽음 퍼프 색**으로만 산다
  (`forest_enemy._apply_look` 주석이 직접 그렇게 적어 뒀다). 그대로 갔으면 **네임드가 덩치만 다르고 색은 그대로**였을 것이다.
  → 몸을 물들이는 키는 **`params.tint`**(세99 신설)이고, `_refresh_tint`에서 상태이상 틴트와 **곱한다**
  (⚠ **대입하면 첫 상태이상에 색조가 영영 지워지는데 에러가 0이다**).
  🔴 **`params.size`는 루트 scale이라 덩치가 곧 히트박스**이고 `_attach_shadow`가 그림자를 파생시킨다 — 키우면 그림자도 따라온다(공짜).
  ⚠ **색만 바꾼 것을 「새 적」이라 부르지 마라**(세54의 결) — 전용 스프라이트는 나중에 `takbon-art`가 그린다.
- 드롭 = 재료 다량 + 고유 아이템. 🔴 **진행(문양)은 절대 여기 걸지 마라** — D6의 근거가 그것이다.

⚠ **네임드는 새 적 종이 아니어도 된다** — 기존 적의 강화판(HP·크기·색)으로 시작해도 성립한다.
전용 스프라이트는 나중에. 단 **색만 바꾼 것을 「새 적」이라 부르지는 마라**(세54의 결).

## 5. 이 설계가 푸는 것 / 안 푸는 것

### 푼다
| 불만 | 어떻게 |
|---|---|
| *"텅 비어 걷기만 한다"* | 걸어가는 곳마다 **지점**이 있다 — 이동이 「이동」이 아니라 「경로 선택」이 된다 |

| *"공간이 하나뿐"* | 탈출구 여럿 + 지점 = **경로가 생긴다**(방을 안 나누고) |

### 10-5. 미결 (F5·사용자가 정한다)

- **어느 챕터에 몇 채** — 🔴 **사용자가 데이터로 채운다**(D14 확정 · 자리는 나무·바위를 피해 사람이 놓는다)
