## ① 현재 상태 (코드 직접 검증)

### 절차 도형 3함수와 그 호출부 (전수)

| 함수 | 위치 | 형식 | 점 수 실측 |
|---|---|---|---|
| `jin_guide_pts(shape, ctr, r)` | `src/drawing/ring_board.gd:436` | `Enums.JinShape` match, **닫힌** 점열 | 73 (=`GUIDE_CIRCLE_N` 72 + 닫음 1, 도형 무관 통일) |
| `rune_guide_verts(rune_type, ctr, s)` | `ring_board.gd:521` | **꼭짓점 3~7개**만 반환 | 호출부 `_build_guide`(:300~305)가 변마다 **12등분** → 최종 37(불△)~73(번개⚡)점 |
| `glyph_guide_pts(code, p, outward, sz)` | `ring_board.gd:344` | 방향 프레임(outward) 기준 열린 획 | 화살표 25점, densify류(관통·팅김·추진) 가변 |

호출부는 **정확히 6곳** (grep 전수 — 발사·저장 계약과는 완전 무관):
- **판**: `_build_guide` 3갈래 (`ring_board.gd:294, 300, 313`)
- **책 셀**: `jin_icon_marks`(`ring_book.gd:371` — static, 윤곽=첫 획), `_draw_rune_icon`(`:472` — verts를 그대로 polyline), `glyph_icon_pts`(`:561` — outward=UP 고정)

즉 "셀에서 본 모양 = 손으로 그을 모양" 규약은 **양쪽이 같은 static을 부르는 것**으로 성립한다. 커스텀도 같은 구조로 끼워야 한다.

### 채점기와의 관계 (핵심 — trace_scorer는 안 건드려도 된다)

`trace_scorer.gd`는 `set_guide(pts)`로 **점열만** 받는다. 모양·종류를 전혀 모른다.
- 완성도 = 드러난 가이드 점 비율 → **점 수가 곧 채점 무게** (도형마다 점 수가 다르면 유불리).
- 정밀도 = 가이드 최근접점 이탈 평균 → 점 **간격**이 REVEAL_RADIUS(0.08R)·붓 자국과 정합해야 함 (세25 화살촉 사건의 원리, `_densify` 주석).
- → **커스텀 점열이 "종류별 고정 점 수 + 균등 간격"이면 채점 공식은 무변.** 가이드 생성 쪽에서 닫힌다.

### 기존 회귀 그물 (유지해야 할 계약)

`tests/test_ring_trace_auto.gd`:
- ⑳(:402) — raw static `jin_guide_pts`에 **닫힘·중심 비움 ≥0.45R·점 수 73±8·8종 상이** 절대치를 박아 둠. 뮤테이션 검출력 확인됨.
- ㉑(:443) — 배선 도달: 임시 JinDef(`load().new()` + 필드 주입)로 `choose_jin` → `guide_points()`가 raw static과 일치 + **책 `jin_icon_marks` 윤곽도 일치**.
- ㉒ 이하 — 룬 6종·문양 상이/폴백 그물.
→ **raw static 시그니처·절차 동작은 그대로 둬야** 이 그물이 산다. 커스텀은 그 위에 얹는다. 임시 def 주입 패턴(㉑)이 커스텀 테스트의 본보기다.

### 저장 도안 호환

`get_assembly()`(:229)는 score·ink·구성 int만 싣는다 — **가이드 기하는 발사·저장에 안 실린다.** 커스텀 도형으로 갈아끼워도 옛 `RingDesign`은 안 깨진다(앞으로 그릴 때의 손 궤적·난이도만 바뀐다).

### .tres 직렬화

`PackedVector2Array`는 text resource 네이티브 지원(`PackedVector2Array(x1, y1, x2, y2, …)`). 도구가 `ResourceSaver.save`로 쓰므로 세50 손편집 오타 함정(3인자 Color류)은 구조적으로 안 밟는다. 단 **로드 검증 그물은 별도로 필요**(⑤).

## ② 스키마 변경안 (리드가 core 반영 — ⑧에 목록)

세 스키마에 같은 필드 하나씩:

```gdscript
## 🔴 커스텀 밑그림 (밑그림 편집 도구가 쓴다). 비어 있으면 절차 도형(guide_shape 등) 폴백.
## 정규화 좌표 — 프레임 규약은 종류마다 다르다 (ring_board의 *_guide_for 래퍼가 변환).
@export var guide_pts: PackedVector2Array = PackedVector2Array()
```

**정규화 프레임 규약** (ctr/r 무관 저장 — 휠 크기·판 크기·셀 크기에 전부 자동 대응):

| 종류 | 원점 | 단위 | 런타임 변환 |
|---|---|---|---|
| 진 (JinDef) | 진 중심 | 반지름 1.0 = 판의 `_jin_radius()` | `ctr + p * r` |
| 룬 (RuneDef) | 룬 중심 | 1.0 = `_rune_size()` (기존 verts와 같은 단위 — 풀🍃이 1.15까지 쓰는 그 좌표계) | `ctr + p * s` |
| 문양 (GlyphDef) | 칸 중심 | 반길이 1.0 = `sz`, **바깥 방향 = `Vector2.UP`** (책 셀이 이미 UP 고정 — `ring_book.gd:561`) | `p + q.rotated(outward.angle() - Vector2.UP.angle()) * sz` |

- 빈 배열 = 커스텀 없음 = 절차 폴백 (하위호환 그대로).
- 문양의 `inward`(응집=안쪽) 방향 뒤집기는 절차 함수 안 로직인데, **커스텀은 그린 그대로**가 정체성이므로 래퍼가 방향을 안 뒤집는다 — "위=바깥" 캔버스에서 안쪽 향하게 그리면 그게 응집 모양이다 (⑨ 결정점 3).

⚠ 스키마 파일은 class_name이라 **Db 참조 금지** 유지 — 이 필드는 순수 데이터라 문제없다. 변환·폴백 판단은 전부 ring_board 래퍼(아래 ③)가 한다.

## ③ 오버라이드 주입 지점 — 대안 비교 + 추천

**A안. 호출부 6곳이 각자 분기** (`if not def.guide_pts.is_empty(): … else: static(…)`)
- ✗ 같은 분기+변환이 6곳에 복사 → "셀=판" 규약이 **호출부 규율**에 의존. 한 곳이 빠지면 셀과 판이 조용히 갈라진다 — 이 프로젝트가 세47·48에 두 번 청산한 바로 그 갈라짐을 되심는 꼴. **각하.**

**B안. 기존 static에 옵션 인자** (`jin_guide_pts(shape, ctr, r, custom := PackedVector2Array())`)
- ○ 시그니처 호환(기존 테스트·호출 생존), 분기가 함수 안 한 곳.
- ✗ "def에서 guide_pts를 꺼내 넘긴다"가 여전히 호출부 6곳의 일 — def 추출 누락 = A안과 같은 침묵 갈라짐. shape와 custom을 둘 다 넘기는 어색한 API.

**C안 (🔴 추천). def를 받는 래퍼 static 신설, raw static은 절차 정본+폴백으로 유지**

```gdscript
# ring_board.gd에 추가 (전부 static — 인스턴스 상태 안 봄, 기존 규약 그대로)
static func jin_guide_for(def: JinDef, ctr: Vector2, r: float) -> PackedVector2Array
static func rune_guide_for(def: RuneDef, ctr: Vector2, s: float) -> PackedVector2Array
static func glyph_guide_for(def: GlyphDef, p: Vector2, outward: Vector2, sz: float) -> PackedVector2Array
```

- 내부: `def != null and not def.guide_pts.is_empty()` → 정규화 변환 / 아니면 raw static 호출. **커스텀 vs 절차 결정 + 좌표 변환이 종류당 한 곳.** def가 null이면 절차 폴백이라 순수 단위 테스트도 그대로 산다.
- 🔴 **룬 래퍼는 12등분 densify를 내부로 흡수해 최종 dense 점열을 반환한다** (질문 3의 답 — 아래 별도 절).
- raw static(`jin_guide_pts` 등)은 **무변** → 기존 뮤테이션 그물 ⑳㉒ 그대로 유효.
- ring_board는 이미 `JinDef`·`RuneDef`·`GlyphDef` 타입을 직접 참조한다(`_jin_def: JinDef` 등) — `-s` 지연 로드 환경에서 이미 돌고 있는 형태라 컴파일 함정 없음. **Db는 여전히 안 본다**(def 주입은 지금처럼 바깥 몫).

**호출부 전환 (6곳):**

| 호출부 | 전환 | def 출처 (전부 이미 손에 있음) |
|---|---|---|
| `_build_guide` JIN(:294) | `jin_guide_for(_jin_def, ctr, _jin_radius())` | `_jin_def` |
| `_build_guide` RUNE(:300~305) | `rune_guide_for(_rune_defs.get(_rune_idx), ctr, _rune_size())` — 12등분 루프 삭제 | `_rune_defs` |
| `_build_guide` GLYPH(:313) | `glyph_guide_for(_glyph_def_by_code(_active), …)` | `_glyph_defs` |
| `ring_book.jin_icon_marks`(:369) | 뒤에 옵션 인자 `def: JinDef = null` 추가(세48 shape 기본값 트릭 재사용 — 옛 5인자 호출 생존). 윤곽 = def 있으면 `jin_guide_for`, 없으면 기존 그대로. 호출부 `_draw_jin_cells`가 jd를 넘긴다 | `jd` (이미 `_jin_shape_of(jd)` 하는 자리) |
| `ring_book._draw_rune_icon`(:471) | `rune_guide_for(rd, c, s)` polyline — dense여도 시각 동일. 시그니처에 `rd: RuneDef = null` 추가, `_draw_rune_cells`가 rd를 넘긴다 | `rd` |
| `ring_book.glyph_icon_pts`(:560) | 인스턴스 함수라 `_glyph_defs`에서 code로 def 조회 → `glyph_guide_for(def, c, Vector2.UP, s)` | `_glyph_defs` |

→ 셀과 판이 **같은 래퍼**를 부르므로 "셀에서 본 모양 = 손으로 그을 모양"이 커스텀에서도 구조적으로 못 갈라진다. 관측점도 기존과 동일(책 쪽 = `jin_icon_marks`/`glyph_icon_pts`, 판 쪽 = `guide_points()`).

### 질문 3 — 룬의 형식 차이 (꼭짓점 vs 조밀 점열)

- **커스텀 룬은 12등분을 건너뛰고 리샘플 점열을 직접 쓴다.** 12등분은 "꼭짓점만 있는 절차 룬을 조밀하게 만드는" 수단이었을 뿐이고, 채점기가 원하는 건 조밀 점열 그 자체다. 손그림 리샘플이 이미 조밀하다.
- `_build_guide`에 있던 12등분 루프는 래퍼의 절차 갈래로 이사한다(절차 룬 결과는 바이트 단위로 동일 — 회귀 0, 뮤테이션 소재).
- **채점 영향 없음**: trace_scorer는 점열의 출처를 모른다. 부작용은 점 수·간격뿐이고 그건 ⑤의 고정 리샘플이 통제한다.
- 부수 효과: 커스텀 룬은 **곡선도 된다** (절차 룬은 다각형뿐이었다). 꼭짓점 3~7 규율은 "호출부가 변마다 12등분하므로"가 이유였는데 그 이유 자체가 커스텀에선 사라진다.
- 책 룬 아이콘이 sparse verts 대신 dense 점열을 polyline하게 되는데 시각 결과는 동일하다.

### ring_board 입력 재사용 여부 (질문 5의 트레이드오프)

**미니 전용 캔버스를 새로 쓴다 (추천).** ring_board의 획 처리는 조립 상태기계(단계 게이트·칸 선택·잉크 정산·휠·펄스)에 깊게 얽혀 있어(1,121줄), 도구가 이걸 몰려면 가짜 조립 단계를 연출해야 한다 — 배보다 배꼽이다. 도구 캔버스에 필요한 건 "좌드래그로 획 배열에 점 쌓기 + 우클릭 지우기 + polyline 렌더"뿐이라 ~120줄이다.
**대신 정본은 이 두 지점에서 재사용한다** (여기가 갈라지면 안 되는 곳이다):
- **최종 가이드 생성 = 래퍼 static** — 미리보기가 게임과 같은 함수로 그린다("도구에서 본 것 = 게임에서 그을 것").
- **자가 채점 = TraceScorer** — 저장 전 검증(⑤)에 그대로 쓴다. 채점 코드 복사 0.

## ⑤ 검증 규칙 표 (도구가 저장 전 강제)

리샘플 = 획들을 이어 총 호 길이 균등 분할. **점 수 고정이 곧 채점 공정성이다** (완성도 무게 = 점 수).

| 규칙 | 진 | 룬 | 문양 | 근거 |
|---|---|---|---|---|
| 리샘플 점 수 | **72 + 닫음 1 = 73** | **48 + 닫음 1 = 49** | **25** (열린 획) | 진 73 = 기존 절차와 동일 + 테스트 ⑳의 73±8 절대치에 그대로 정합. 룬 49 = 절차 룬 실측 범위(37~73)의 중앙. 문양 25 = 화살표 실측 |

### 로드 검증 그물 (세50 「조용한 데이터 죽음」 대응 — 질문 1 후반)

1. **도구 안 즉석 그물**: 저장 직후 `ResourceLoader.load(path, "", ResourceLoader.CACHE_MODE_IGNORE)`로 재로드해 guide_pts 크기 확인. ⚠ **그냥 `load()`는 같은 프로세스 캐시를 돌려줘 디스크 쓰기가 실패해도 통과한다** — 검출력 0. 캐시 우회가 이 그물의 전부다.
2. **스위트 그물** (`test_ring_trace_auto`에 ㉓으로 추가, test_decode_auto 「룬 6종 로드」 방식):
   - Db 경유 로드 수: 진 8·룬 6·문양 6이 전부 로드된다 (한 장이 파싱 실패로 죽으면 여기서 갈라진다).
   - guide_pts가 **있는** def마다: 래퍼 출력 ≠ 절차 출력(커스텀이 실제로 이긴다) · 점 수 = 고정치 · 진/룬 닫힘 · 진 중심 비움 · 이웃 간격.
   - 배선 도달: 임시 def에 guide_pts 주입 → `choose_jin`/`choose_rune` 후 `guide_points()` = 래퍼 출력 (기존 ㉑ 패턴 복제) + 책 `jin_icon_marks`/`glyph_icon_pts`도 동일 점열.
   - **뮤테이션 소재**: ⓐ 래퍼가 custom을 무시하고 절차만 반환 → "커스텀이 이긴다" + 배선 그물 실패 ⓑ 래퍼의 좌표 변환에서 `* r` 누락 → 점열 불일치 실패 ⓒ 룬 래퍼의 절차 갈래 12등분 제거 → 절차 룬 점 수 그물 실패.

## ⑥ UX 흐름

```
[탭: 진(8) | 룬(6) | 문양(6)]   ← Db 전 목록 (해금 무시 — 개발 도구. ⑨ 결정점 4)
   셀 클릭 (셀 아이콘 = 래퍼 static → 커스텀 있으면 이미 그 모양)
      ↓
[왼쪽 캔버스]
   · 어니언 스킨: 현재 모양(커스텀 or 절차)을 연하게
   · 종류별 보조선: 진 = 0.5 금지원(빨강) + 1.0 기준원 + 1.15 상한원
                    룬 = 단위 원(1.0) 기준선
                    문양 = ↑바깥 축 화살표 + 1.1 길이 눈금
   · 좌드래그 = 획 (여러 획 OK — 단 직전 획 끝 근처에서만 시작)
   · 우클릭 = 전부 다시 (본게임 규약 그대로)
      ↓
[미리보기 ▶]  ← 리샘플 결과를 굵게 겹쳐 그림 + 검증 체크리스트(✓/✗ 사유 문구)
   · 함께 표시: "책 셀에서 보일 모습" 소형 렌더 (같은 래퍼 — 규약 시각화)
   · 문양은 8칸 중 한 칸 각도로 회전한 샘플도 (회전 변환 눈 확인)
      ↓
[저장]  ← 검증 전부 ✓일 때만 활성. ResourceSaver → 캐시 우회 재로드 → 결과 문구
[절차 도형으로 되돌리기]  ← guide_pts 비워 저장 (탈출구 — 옛 도형 안전망 복귀)
```

기존 책 셀 규약과 맞물리는 지점: 저장하면 다음 실행(또는 Db.reload)부터 **책 셀·판 밑그림·룬 아이콘이 동시에** 새 모양 — 래퍼 단일 소스의 결과라 별도 배선이 없다.

⚠ 도구도 화면 덮는 Control 조합이다 — 캔버스는 `MOUSE_FILTER_STOP`(ring_board와 동일), 배경 장식은 `mouse_filter = 2`. 클릭 도달은 헤드리스가 못 잡으므로 리드 실게임 확인 항목에 포함(⑦).

## ⑨ 사용자 결정점

1. **리샘플 고정 점 수** — 진 73 · 룬 49 · 문양 25 (시작값). 승인 여부.
2. **진 중심 비움 하드 제약 0.5R 유지** — 더 파고드는 진을 그리고 싶으면 룬과 겹친다. 유지 추천.
3. **문양 방향 규약** — 캔버스 "위 = 바깥(진 쪽)". 응집처럼 안쪽을 향하는 문양은 **아래를 향해 그린다** (절차 응집의 자동 방향 뒤집기를 커스텀엔 적용 안 함 — 그린 그대로가 정체성). 이 규약이 직관적인지.
4. **도구는 해금 무시하고 전 목록 노출** (개발 도구니까). 승인 여부.
5. **곡선 룬 허용** — 커스텀 룬은 다각형 제약이 사라져 곡선도 등록된다. 룬의 "인장" 정체성상 문제없다고 보지만 확인.
6. **절차 도형의 지위** — 설계는 "폴백 + [되돌리기]의 목적지"로만 남긴다(선택지 병존 아님). 확정 방향 3항과 일치하지만 명시 확인.
