## 한 문장

**진 = 하나의 해석 규칙(틀). 그 틀 안에서 각 룬을 문양으로 감싸고(안→밖 = 연산 순서), 진 규칙이
그 감싸진 룬 뭉치들을 하나로 합쳐 마법이 나온다.**

같은 재료(룬·문양)라도 **어느 진에 넣느냐 · 어느 순서로 감싸느냐**에 따라 결과가 통째로 달라진다.
이게 세68 모델("마법진 = 수식")의 **내부 구조를 실제로 채우는** 설계다.

## 두 겹 분리 (이 설계의 심장)

모델을 두 겹으로 쪼갠다. **이 분리가 "손으로 짤 양"을 유한하게 만드는 핵심이다.**

### ① 룬 한 개를 감싸는 규칙 = 전 진 공통 (한 번 정하면 끝)

- 룬 하나 = **중심 씨앗(속성)**. 그 바깥으로 문양이 겹겹이 감싼다.
- **안쪽부터 바깥쪽으로 해석** = 연산 순서. 안쪽 문양 먼저 계산, 그걸 바깥 문양이 감쌈.
- 예: `불`을 안에, `확산`으로 감싸고, 그 위를 `폭발`로 감싸면 → `폭발(확산(불))`.
- 🔴 **이 규칙은 진마다 다시 안 만든다.** 전 진 공통 기계 규칙. 한 번 구현하면 끝.

**순서가 결과를 바꾼다** (세68 미결 1번 → 여기서 "바꾼다"로 확정):

| 배치 (안→밖) | 수식 | 결과 |
|---|---|---|
| 불 → 확산 → 폭발 | `폭발(확산(불))` | 넓게 깔린 뒤 광역 폭발 |
| 불 → 폭발 → 확산 | `확산(폭발(불))` | 작게 터지며 파편이 사방으로 튐 |

같은 재료, 순서만 바꿔 완전히 다른 마법 → 조립이 진짜 **수식**이 되는 지점.

### ② 여러 룬 뭉치를 "어떻게 합치나" = 진마다 bespoke 해석

- 룬이 2개 이상이면, 각자 감싸진 뭉치를 **진이 어떻게 버무리느냐**가 진의 개성.
- 🔴 **여기가 "진마다 해석이 다르다"가 사는 유일한 자리.** 진 하나당 규칙 하나.
- 예 (재료: `확산(불)` + `응축(물)`, 즉 "퍼지는 불" + "뭉치는 물"):
  - **순환진** (규칙 = 번갈아 순환) → "퍼진 불 ⇄ 뭉친 물" 교대로 나감
  - **융합진** (규칙 = 섞음) → "끓는 물안개" 한 덩이
- 🔴 **손으로 짜는 건 조합마다가 아니라 "이 진은 뭉치들을 어떻게 합치나" 딱 하나씩.**
  불+확산+물+응축의 모든 경우를 일일이 authoring하지 않는다 — 진의 "합치는 성격"만 정한다.
- 🔴 **지금 만드는 게 아니다.** 진별 해석은 나중에 진을 추가할 때마다 손으로 짠다.
  이 설계는 **그 자리를 비워두는 것**이지, 지금 순환진·융합진을 구현하자는 게 아니다.

## 그림

```
┌──── 진 : 순환진   (② 진 규칙 = "번갈아 순환") ────┐
│                                                    │
│    [룬 자리 1]                [룬 자리 2]           │
│   ╭─ 확산 ─╮                ╭─ 응축 ─╮            │  ← 바깥 = 문양 (감쌈, 층)
│   │  불   │                │  물   │            │  ← 안쪽 = 룬 (씨앗)
│   ╰───────╯                ╰───────╯            │
│   = 퍼지는 불               = 뭉치는 물            │  ① 룬마다 감쌈 (전 진 공통)
│                                                    │
└────────────────────────────────────────────────────┘
              ↓  ② 진 규칙이 둘을 합침 (진마다 다름)
        "퍼진 불 ⇄ 뭉친 물" 교대로 나가는 마법
```

- **안쪽 = 룬 · 감싸는 바깥 = 문양** — 자리마다 작은 양파.
- **자리 개수·위치 = 진 모양이 정함** (동그라미 1자리, 순환진 2자리…).
- **양파들을 어떻게 하나로 합치나 = 진 규칙** (②).

진 만들 때 손으로 정하는 것 = **딱 두 가지**:
1. **룬 자리가 몇 개, 어디에** (모양)
2. **그 자리들을 어떻게 합치나** (규칙)

## 확정된 규칙 (대화로 잠근 것)

- **진 = 바깥 껍질(그릇). 안쪽부터 룬 → 문양 → 문양** 순으로 감싸며 나간다.
- **층(밴드) 깊이 = 연산 순서.** 안쪽 층 먼저 해석, 바깥 층이 그걸 감쌈.
- **문양 하나가 층 1~2개를 점유할 수 있다.** 2층 점유 = 그 두 층을 통째로 먹음 →
  거기에 1층짜리 문양 2개를 못 넣는다. (크고 세지만 자리값이 비쌈 = 트레이드오프.)
- **진마다 룬 개수 = 2~6개** (진 만들 때 그 진에 맞게 정함). 진 모양이 룬 자리 수를 정한다.
- **룬 ↔ 문양 짝은 고정 아님.** 대체로 전 조합 가능. 일부 불가 조합은 나중 여지 (지금 안 박음).
- **문양도 진처럼 밑그림(본)으로 손으로 그린다** — 조립 대상이자 탁본 대상. (세68 정체성 유지.)
- **문양이 영향 주는 대상 = 그 문양이 감싸는 안쪽(룬 또는 안쪽 문양 뭉치).**
  룬 자리 위에 놓으면 그 룬을, 바깥 공용 층에 놓으면 안쪽 전체를 감싼다.

## 첫 변형 문양 — 확산·폭발 (M1 콘텐츠, ✅ 확정 세78)

지금 문양(응집·발산)은 **독립 착탄 전개**라 순서가 무의미하다. M1의 순서 실증을 위해 **변형형 문양**
(안쪽 결과를 감싸 바꾸는 연산자) 2종을 정의한다:

- **확산 (퍼뜨림)** — 안쪽 결과를 **여러 갈래/넓게 편다.** (한 줄기 → 부채꼴, 좁은 것 → 넓은 것)
- **폭발 (터뜨림)** — 안쪽 결과를 **한 점에서 광역으로 터뜨린다.** (착탄 AoE)

**순서가 만드는 차이 (M1 성공 기준 = 이게 눈에 보이면 성공):**

| 배치 (안→밖) | 수식 | 결과 |
|---|---|---|
| 불 → 확산 → 폭발 | `폭발(확산(불))` | 넓게 편 뒤 통째로 터뜨림 = **넓은 지역 광역 한 방** |
| 불 → 폭발 → 확산 | `확산(폭발(불))` | 터뜨린 뒤 여러 갈래로 폄 = **작은 폭발 다발이 부채꼴로** |

- 🔴 **수치(퍼짐 각도·갈래 수·폭발 반경·피해)는 전부 balance.tres 시작값, F5로 조인다.**
- ⚠ **이름 겹침 주의**: "확산"은 **바람 룬**이 이미 쓴다(바람 = 상태를 옆 적에 옮기는 확산자, `status_rules`).
  문양 확산(마법을 기하적으로 폄)과 개념이 다르다 — 구현 시 이름 충돌 정리(문양 id는 별도, 표시명 재검토).
- 계약: 확산·폭발도 `GlyphRingDef.motif`가 **새 GlyphCode 값을 참조**하는 방식(세70 규약). `Enums.GlyphCode`에
  값 추가는 되지만 기존 값(GATHER=0/RADIATE=1)은 **밀지 않는다.** 변형 연산자는 착탄 전개(응집·발산)와
  **다른 계열**이라, 발사 해석기가 "전개형 vs 변형형"을 구분해 변형형은 안쪽 결과에 함수처럼 적용한다.

## 남은 조각 — 추천안 (세78 교차 감사 반영 · ⏳ 사용자 최종 확인 대기)

전부 **기존 문서·라이브 코드와 정합되게** 채웠다(감사가 확인한 조립 UI 체인 위에 앉힘). 뒤집고 싶으면 말해라.

1. ✅ **진 등급 = 층 수 (사용자 확정 세78)** — 확정이라 더 안 연다.
   - **진에 등급이 있다. 등급은 오직 층 수만 정한다** (위력·다른 축과 무관).
     `N등급 = N층 = 룬 하나를 감쌀 수 있는 문양 겹 상한`.
   - 🔴 **숫자가 클수록 높다** (1등급 < 2등급 < 3등급 …). **상한 9등급** — 사용자: *"내가 얼마나 확장할지 몰라서"*.
   - **축 두 개로 갈린다**: **진 종류**(일반진·순환진… = 룬 자리 배치 + 합치는 규칙 = 성격) × **등급**(층 수 = 얼마나 깊게).
     같은 종류의 다른 등급이 공존한다 — `일반진 1등급`·`일반진 2등급`·`일반진 3등급`. 파밍 감각과도 맞물림.
   - 🟢 **새 스키마 0 — `JinDef.band_count`가 곧 등급이다.** `.tres` 한 장에 `band_count = N` + 표시명 "N등급"이면 끝.
     (별도 grade 필드를 만들면 band_count와 갈라진다 — 단일 소스 규율.)
   - 1등급(1층) = 1겹뿐이라 **감쌀 순서가 안 생긴다**. **2등급부터 `폭발(확산(불))`이 가능**해진다.
   - ⚠ **기하 한계**: `BAND_RADII = [0.42, 0.68]`로 **지금 2겹까지만** 정의돼 있다. 3등급 이상을 넣으려면 반경 목록을 늘려야 하고,
     🔴 **실제로 손으로 그을 수 있는 겹 수의 상한은 판 크기·정밀도 tolerance가 정한다**(밴드 간격이 tolerance보다 충분히
     커야 함 — 세50 「반경 실측」 교훈). **스키마 상한 9는 확장 여지이고, 실용 상한은 F5로 잰다.**
   - ⚠ 이름 겹침: 게임에 이미 **도안 등급**(`ring_power.grade_of` — 얼마나 잘 그렸나)·**아이템 등급**(`grade_colors.gd` — 희귀도)이
     있다. 진 등급이 세 번째라 UI 표기는 구현 때 정리("3등급 일반진" 식으로 진 이름에 붙이기 추천).
2. **진 규칙(②) 표현** — 추천 = **코드 분기로 시작**(진 id → 합치기 함수). 진이 몇 개 쌓여 공통 패턴이 보이면 그때 데이터로 추출.
   지금 없는 걸 미리 스키마화하지 않는다(YAGNI · 세47 「안 켠 배선」 교훈). ⚠ 위력에 개입하면 `ring_power` 단일 소스.
3. **문양의 "기본 의미"** — 추천 = **문양은 기본 뜻이 있다**(확산=퍼짐, 폭발=터짐). 진 규칙은 **②(여러 룬 합치기)에서만 개입**한다.
   ①의 감쌈 의미까지 진마다 뒤집으면 **손으로 짤 양이 폭발**하고 플레이어도 문양을 못 외운다.
4. ✅ **확산·폭발 = M1 첫 변형 문양으로 확정** (위 「첫 변형 문양」 절). 이후 어휘(응축·관통·가속…)는 후속.
5. **조립 UI 표현** — 추천 = **기존 책 조립 UI(밴드 소켓)를 그대로 쓰고 단계적으로 넓힌다**.
   감사가 확인: 조립 UI 체인(책 재설계→Phase 게이트→밑그림 시각 층→`draw_tools_panel`)은
   **내부 정합·라이브와 일치**하고, 이 설계의 감쌈-층은 그 밴드를 토대로 채택한다.
   ⚠ 세87: 그 체인 문서 중 `draw_tools_panel_design.md`만 남고 앞의 셋은 **구현 완료 아카이브라 삭제**했다
   (라이브 코드 = `ring_forge_panel.gd:174` `enum Phase` · `ring_board.gd:625` `compose_guide_paths`).
   - **M1 (룬 1개)** = 각도 구분 불필요 → **깊이(밴드 순서)만** 쓴다. 기존 밴드 소켓 UI 거의 그대로. UI 신규 공사 최소.
   - **M2 (룬 2개+)** = 그때 **각도(어느 룬 자리)** 축을 추가 → 「각도 × 깊이」 격자 완성.
   - 🔴 실제 손맛(밴드 간격이 정밀도 tolerance의 몇 배인지 등)은 **F5로만** 정해진다(세50 좌표 실측 교훈).
6. **크게 조립할수록 탁본이 길고 어려워진다** — 추천 = **의도로 남긴다.** 층·문양이 많은 진 = 긴 정밀 탁본 =
   자연스러운 리스크·리워드("센 마법진은 그리기 어렵다"). 세68 정본이 이미 이걸 "의도로 남기면 좋음"이라 적었다.
   ⚠ 다만 **지겨움으로 넘어가는 경계는 F5로 확인**(감사가 남긴 실측 목표).

## 기존 설계·코드와의 관계 (🔴 회귀 정직하게 — architect 리뷰 반영, 세78)

이 설계는 순수 오버레이는 아니지만, **처음 생각보다 이행이 얕다** — architect가 실측으로 밝혔다:
**우리가 "새로 지어야 한다"고 본 "안쪽부터 감싸는 층"이 세70에 이미 밴드(동심원 층) 파이프라인으로
지어져 있다.** 지금은 그 층을 발사 직전에 뭉갤 뿐이다.

- **`takbon_model.md` (세68)** — 상위 루프(파밍→조립→탁본→발사)는 그대로. 이 문서는 그 중
  **"조립본이 어떤 구조인가 · 어떻게 해석되나"**를 확정한다. 세68의 미결 1번(순서=연산)을 "산다"로 답.

- 🟢 **세70 밴드 파이프라인 = 이 설계의 이행 기준선 (이미 있는 배선, architect 실측)**:
  - `GlyphRingDef` = `motif(GlyphCode) × count` — **밴드에 끼우는 파밍 단위** (문양-고리).
  - `ring_board.compose_guide`/`compose_guide_paths`/`flatten_bands` — 진 윤곽+룬+**밴드별 문양-고리**를
    한 장 가이드로 합성 → `TraceTarget.COMBINED`로 통째 트레이스.
  - `BAND_RADII`(동심원 2겹)·`_bands` 소켓 — **"층"이 이미 데이터·기하·UI로 실재한다.**
  - 🔴 그래서 이 설계의 "감쌈 층"은 **새로 발명이 아니라, 이미 있는 밴드에 「연산 순서」 의미를 주는 일**이다.
    지금 `flatten_bands`가 밴드들을 8칸으로 뭉개 **순서를 버린다**(라운드로빈). 이행 =
    **"flatten을 걷고 밴드를 순서 있는 층으로 발사까지 들고 간다."** 세70 슬라이스 설계의 Q5가
    예고한 승격 경로 그대로다(그 문서는 승격이 M1으로 집행돼 세87에 삭제 — 후계가 이 문서다).

- 🔴 **`nested_design.md` = 프레임 대체 (공존 아님, architect 확정)**:
  - nested의 프레임(평평한 `runes[]` 자동 반응 · 8칸=착탄 전개 · **재귀 자식 진 배달**)은
    **세68·72 이전 가정**(진이 날아감·문양=8칸) 위에 서 있어 토대가 은퇴했다. 이 문서가 그 개념 프레임을 **대체**한다.
  - **단, nested의 코드 인벤토리는 흡수한다** — architect 재확인: `projectile.gd`의 `rune_hits`(`:88/:138/:365`)·
    `ring_carrier.deployed`·rune_fill 소비자 0곳 진단 전부 실재. 이 기계들은 M2 합치기·상태 세기에서 재활용.
  - **원소 반응(`status_holder`)은 이 설계 ②「진 규칙」의 한 인스턴스로 앉는다** — "융합진 = 섞음"이 곧
    젖음+번개=감전이다. nested의 "평범 배열 자동 반응"은 **범용 기계가 아니라 특정 진(융합진)의 합치기 규칙**으로 격하.
  - → `README` 인덱스에서 nested_design을 "참고 자산(코드 실사·rune_fill 결정)"으로 갱신 (리드 몫).

- 🟡 **닿는 core (이행이 얕음 — architect 실측)**:
  - **`RingDesign.rings: Array`가 이미 배열의 배열을 담게 돼 있다.** 지금 `get_assembly()`가 `[Array]` 한 겹만,
    `_on_ring_cast`가 `rings[0]`만 본다. **층 살리기 = 새 트리 스키마가 아니라 "rings를 다겹으로 채우고
    발사부가 밴드 루프를 돈다."**
  - 🟢 **무회귀 폴백 실재 성립** (architect 코드로 뒷받침): 옛 평평한 도안(`rings=[8칸]` 한 겹)은
    "감쌈 0겹/층 1개"로 그대로 해석 · `score` 없으면 기준 위력 폴백 · `set_motion` 미호출 = 픽셀 동일 →
    옛 도안·옛 세이브 안 깨짐.
  - ⚠ **단 flatten을 걷으면 발사부가 갈라진다**: `_deploy_now`가 `rings[0]`만 돌던 걸 밴드 루프로 넓히는 순간,
    **밴드 순서를 전개에 어떻게 반영하나**가 새 규칙 = 발사 계약 해석 확장 → **뮤테이션 그물 필수**
    (옛 한 겹이 여전히 동일하게 나가는지 + 다겹 순서가 실제로 다르게 나가는지 둘 다).

### ⓐ 먼저 사용자와 합의할 것 (코드보다 이게 먼저다 — `takbon-design` 스킬로 대화)

M2는 M1과 달리 **결정점이 남아 있다.** 혼자 정하지 마라(세71 교훈: 서브에이전트가 혼자 정해 사용자
생각과 달라졌다).

1. 🔴 **첫 진 규칙(②)을 뭘로 하나** — 설계 예시는 순환진(번갈아 순환)·융합진(섞음)이지만 **확정 아니다.**
   "재밌는 합치기"는 진을 실제로 만들며 발견한다고 이 문서가 이미 적었다(§손맛·밸런스).
   ⚠ 후보 하나는 **이미 게임에 있다**: 원소 반응(`status_rules`)이 곧 "융합진 = 섞음"이다
   (젖음+번개=감전). 그걸 특정 진의 규칙으로 격하해 쓰면 **새 기계 0**으로 M2가 설 수도 있다.
2. **룬 2개를 조립 UI에서 어떻게 고르나** — 지금은 룬 탭에서 하나 고르면 끝(`_rune_picked`).
   자리를 먼저 고르고 룬을 넣나, 룬을 고르면 빈 자리에 채워지나?
3. **룬 자리마다 감쌈 층이 따로인가, 공용인가** — 설계 그림은 자리마다 작은 양파(따로)인데,
   그러면 밴드 소켓이 자리 수만큼 늘어난다. **탁본 길이가 곱으로 늘어난다**(아래 ⓓ 위험).
4. **밑그림에서 룬 2개를 어디에 그리나** — 지금 룬은 중심 하나(`RUNE_GUIDE_FRAC`).
   자리가 2개면 중심을 나눠야 하고, 그건 **손으로 긋는 궤적이 바뀐다**는 뜻이다.

### ⓓ 🔴 M2의 진짜 위험 (M1 F5 결과에 종속된다)

**감싸진 룬 뭉치가 ②의 입력 단위**라, M1에서 나온 문제는 M2가 **곱해서** 물려받는다:
- M1에서 "층 2겹 긋기가 지겹다"면 → M2는 **룬 2개 × 각 층** = 탁본이 배로 길어진다.
- M1에서 "순서 차이가 눈에 안 띈다"면 → ②의 차이는 더 미묘해서 **더 안 보인다**.
🔴 **그래서 M2 착수 전에 M1을 F5로 확인하는 게 순서다**(세79 리드 권유). 결과에 따라 M2의
"룬 자리마다 층 따로"(위 ⓐ-3)를 "층은 공용"으로 접어야 할 수도 있다.

#### ✅ F5 확인 결과 (세80) — **동작 확인 · 세부 소감 미수집**

사용자가 실게임으로 M1을 확인했다: *"이거 되긴하네"* → **층 순서가 실게임에서 실제로 다른 마법을
낸다**(발사가 죽어 있거나 순서가 무시되는 실패는 없다). 세79 세이브(`user://save/rings/`)에 F5용
도안 3장이 이미 장착돼 있다 — 슬롯1 `폭발(확산(불))` · 슬롯2 `확산(폭발(불))` · 슬롯3 대조군(순수 파이어볼).
**다음 세션도 그대로 쓸 수 있다**(세이브 새로 만들 필요 없음).

⚠ **미수집 = ⓓ가 물은 두 질문의 답**: ①2겹 긋기가 지겨운가 ②순서 차이가 눈에 띄는가.
그래서 **ⓐ-3(자리마다 층 따로 vs 공용)은 여전히 미결**이다. M2 첫 대화에서 이걸 먼저 묻거나,
보수적으로 **층 공용**을 택한다(뒤집기 쉬운 쪽).

#### 🔴 세80 헤드리스 실측 — **순서 차이가 「세기」로는 안 갈린다** (M2 설계에 직접 영향)

두 순서를 balance 실값으로 계산했다(확산 3칸·폭발 1칸, `_spread`/`_explode` + `spread_branch_mult=0.6`·
`blast_base_radius_px=54`·`blast_radius_per_branch=0.18`·`blast_merge_mult=0.85`):

| 배치 | 나가는 것 | 반경 | 세기 |
|---|---|---|---|
| `폭발(확산(불))` | 융합 폭발 **1개** | 73px | 1.53 |
| `확산(폭발(불))` | 복제 폭발 **3개** (중심서 44px 흩어짐) | 각 54px | 각 0.51 (**합 1.53**) |

## 왜 얕지만, 처음 생각만큼은 아니다 (architect 실측 세81 반영)

M1이 얕았던 건 층이 이미 밴드로 있었기 때문이다. M2도 재활용할 배선이 있으나, **처음 설계가
"잠든 rune_hits를 채우기만 하면 적 계약 무변경"이라 적은 건 라이브 코드와 어긋났다** — 정정한다.

- 🟢 **복합 룬 기계의 뼈대는 있다** — `src/spell/projectile.gd:85-88`(`rune_hits`) ·
  `:365-368`(순회하며 primary 외 룬을 얹는 루프). 구조(배열로 여러 룬 정보를 나른다)는 재활용한다.
- 🔴🔴 **그러나 "적 계약 무변경"은 틀렸다** (지적 1) — `forest_enemy.take_hit`(`:733-761`)·
  `dummy_target.take_hit`(`:70-84`)는 피해가 얼마든 **무조건** `enemy_hit`을 발신하고 `_pop()`·
  `_play_hurt()`를 돌린다(`if dmg>0` 가드는 **존재한 적이 없다** — `projectile.gd:362-363` 주석이 거짓).
  한 발이 룬 2개로 `take_hit`을 2번 부르면 **피해숫자·히트스톱·팝이 2번** 나 도배가 된다.
  → 🔴 **적 계약에 「직격 피해가 0인 히트는 손맛/발신을 건너뛴다」 가드를 넣어야 한다**(core 변경,
  아래 ⑤·⑥). 이건 회귀 위험이 있어 뮤테이션 필수. **설계가 이 변경을 숨기지 않는다.**
- 🟢 **층이 공용이면 감쌈 해석이 한 번만 돈다** — 룬이 2개여도 `_apply_layer` 루프·명령 목록
  **구조는 그대로**고, 달라지는 건 각 명령이 싣는 **명중 정보(rune_hits)**뿐이다.
  ⚠ 다만 그 정보를 나르는 **스레딩 체인**(`_on_ring_cast`→`_spawn_carrier`→carrier `bind`→
  `_deploy_now`→`_fire_hit`→`_spawn_bolt/pillar/blast`)을 전부 넓혀야 한다 — 특히 **carrier의
  `bind`가 단일 `rune_type`을 나르는 자리**(`:118`)가 놓치기 쉽다. "달라지는 건 `_fire_hit`뿐"은 과소평가.

**두 룬 피해 = 한 히트에 합산** (지적 3 확정 — 사용자: *둘 다 0.7씩, 합 1.4*):
🔴 primary 히트가 **두 룬 피해를 합산해 `base × (0.7+0.7)=1.4`**를 지고, 상태는 primary 상태를 얹는다.
보조 룬은 **직격 0 + 상태 전용 히트**로 얹는다(위 0-피해 가드가 도배를 막는다). 이렇게 해야
사용자의 "합 1.4"(반응 안 나도 단일 1.0보다 셈)와 도배 방지가 **동시에** 선다.

⚠ **`pillar`·`blast`엔 `rune_hits`가 없다**(단일 상태만: `pillar.gd:37`·`blast.gd:60`).
융합진이 응집(기둥)·폭발과 만나면 보조 룬이 조용히 사라진다 → **같은 패턴을 두 씬에 이식**한다
(설계상 새 개념 0, 코드 두 곳). 🔴 이걸 빠뜨리면 "탄으로 쏘면 반응이 나는데 기둥으로는 안 난다"는
**설명 불가능한 갈라짐**이 된다.

## ① 구조 — 씨앗의 목록화

```
지금 (M1):   룬 1개 ──┐
                      ├→ 층 감쌈(공용) → 명령 목록 → 각 명령이 fire(룬1) 로 스폰
M2:          룬 목록 ─┘                              ↑
                                       ② 진 규칙이 「어느 명령이 어느 룬을 싣나」를 정한다
```

- **층 감쌈(①)은 전 진 공통·무변경.** 확산·폭발·발산·응집 전부 그대로.
- **② 진 규칙 = `진 id → 배정 함수`** — 코드 분기로 시작(YAGNI, 데이터화는 진이 쌓인 뒤 = M3).
  - **융합진** = 모든 명령이 **룬 전부**를 싣는다. primary(피해 합산+상태) + 나머지(0-피해 상태 히트).
  - (나중) **순환진** = 명령을 번갈아 룬에 배정 — 같은 자리에 얹히는 확장이라 M2에서 구현 안 함.
- 🔴🔴 **룬 얹는 순서를 정렬한다** (지적 2 — 반응 순서 의존 제거): `status_holder.apply_incoming`은
  **순차**고 `REACTIONS` 표(`status_rules.gd:32-53`)는 **비대칭**이다(base 키가 `WET`·`BURN`·`ROOT`뿐).
  그래서 상태를 얹는 순서에 따라 **같은 두 룬이 반응하기도 안 하기도** 한다 — 물→번개=감전 ✅ /
  번개→물=반응 없음 ❌. **플레이어가 이유 없이 겪는 버그다.**
  → 🔴 **`status_rules`에 대칭 판정 헬퍼**(예: `react_pair(a,b)` = A→B 실패 시 B→A 시도, 또는
  "base로 등장하는 상태를 남기는 룬을 primary로" 정렬 키)를 두고, 융합 발사가 **반응이 나는 순서로
  정렬해 얹는다.** ⚠ 이건 방향(재미)이 아니라 기계 정합이라 설계가 안을 박는다 — **정렬 채택**
  (양방향 시도는 3룬 이상에서 조합 폭발). core 변경이라 아래 ⑤에 올린다.
- **위력** = 룬마다 `multi_rune_share`(balance 시작값 **0.7**) 배 → primary가 **합산**해 진다
  (2룬 = 1.4). 룬 1개면 배율 없음(1.0) = 🔴 **옛 도안 무회귀의 자리**.
- ⚠ **취약 이중 증폭 주의** (지적 5 — CLAUDE.md 「남은 빚」): 융합진이 흙을 포함하면 취약+반응이
  **한 발에** 성립해 이중 증폭 빚에 실제로 닿는다(지금까지는 두 발 필요). **살릴지/자를지는 구현
  세션 초에 결정**(중첩진 M1과 같이 정하기로 한 `nested_design.md ⑧-7` 자리) — 설계는 이 상호작용을
  명시만 하고 수치는 안 박는다.

## ② 첫 진 = 융합진 (`jin_fuse`)

| 필드 | 값 | 이유 |
|---|---|---|
| `rune_slots` | **2** | 신설 필드(기본 1) |
| `band_count` | **2** | 층 순서(M1)를 계속 쓴다 — 융합 × 순서가 곱해지는 걸 실제로 본다 |
| 층 소속 | **공용** | 하드 제약(긋는 양) |
| `pattern`·`motion`·`guide_shape` | 기존 값 재사용 | 새 기하 0 |

**놀이 방식**: "어떤 둘을 붙이느냐"가 선택이 된다 — 젖음+번개 = 감전 연쇄(이득) · 불+물 = 꺼짐(손해) ·
불+풀 = 산불 · 젖음+흙 = 진흙. **반응표는 이미 `src/core/status_rules.gd`에 있고 안 건드린다.**

⚠ **획득 경로는 M1과 같은 임시 시드**(`GameState._seed_starting_unlocks`) — 사용자 방침 *"일단
만들기만 하면 됨"*. 경로를 붙이는 세션이 M1의 3줄과 함께 걷는다.

## ③ 밑그림 — 룬 2개를 중심 좌우로

- 지금 룬은 중심 하나(`RingBoard` `RUNE_GUIDE_FRAC`). 자리 2개면 **중심을 좌우로 나눠 작게 둘**.
- 🔴 **긋는 양**: 진 윤곽 1 + 룬 2(각각 작아짐) + 밴드 2 — 룬이 3개가 돼도 밴드는 그대로.
- 🔴 **자리 위치는 `rune_slots`에서 파생한다**(중심 둘레 균등 배치 — `RingBoard.slot_angle`이 문양 칸에
  쓰는 것과 같은 결). ❌ **배치 좌표 필드를 신설하지 않는다** — 진마다 다른 배치가 실제로 필요해질 때
  필드 한 장을 더한다(`glyph_slots`·`band_count` 선례처럼 기본값이 있어 무회귀).
  ⚠ 같은 이유로 **「층 소속(공용/자리별)」 필드도 M2에선 안 만든다** — 첫 진이 공용만 쓰므로 소비자가
  0곳이 된다. 이 프로젝트엔 이미 그렇게 죽은 축(`rune_fill`)이 빚으로 남아 있다.

### ⓐ 먼저 사용자와 합의할 것 (코드보다 이게 먼저)
