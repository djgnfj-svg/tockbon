## 한 문장

**진 = 하나의 해석 규칙(틀). 그 틀 안에서 각 룬을 문양으로 감싸고(안→밖 = 연산 순서), 진 규칙이
그 감싸진 룬 뭉치들을 하나로 합쳐 마법이 나온다.**

같은 재료(룬·문양)라도 **어느 진에 넣느냐 · 어느 순서로 감싸느냐**에 따라 결과가 통째로 달라진다.
이게 세68 모델("마법진 = 수식")의 **내부 구조를 실제로 채우는** 설계다.

## 두 겹 분리 (이 설계의 심장)

모델을 두 겹으로 쪼갠다. **이 분리가 "손으로 짤 양"을 유한하게 만드는 핵심이다.**

### ① 룬 한 개를 감싸는 규칙 = 전 진 공통 (한 번 정하면 끝)

- 룬 하나 = **중심 씨앗(속성)**. 그 바깥으로 문양이 겹겹이 감싼다.
- **안쪽부터 바깥쪽으로 해석** = 연산 순서. 안쪽 문양 먼저 계산, 그걸 바깥 문양이 감쌈.
- 예: `불`을 안에, `확산`으로 감싸고, 그 위를 `폭발`로 감싸면 → `폭발(확산(불))`.
- 🔴 **이 규칙은 진마다 다시 안 만든다.** 전 진 공통 기계 규칙. 한 번 구현하면 끝.

**순서가 결과를 바꾼다** (세68 미결 1번 → 여기서 "바꾼다"로 확정):

| 배치 (안→밖) | 수식 | 결과 |
|---|---|---|
| 불 → 확산 → 폭발 | `폭발(확산(불))` | 넓게 깔린 뒤 광역 폭발 |
| 불 → 폭발 → 확산 | `확산(폭발(불))` | 작게 터지며 파편이 사방으로 튐 |

같은 재료, 순서만 바꿔 완전히 다른 마법 → 조립이 진짜 **수식**이 되는 지점.

### ② 여러 룬 뭉치를 "어떻게 합치나" = 진마다 bespoke 해석

- 룬이 2개 이상이면, 각자 감싸진 뭉치를 **진이 어떻게 버무리느냐**가 진의 개성.
- 🔴 **여기가 "진마다 해석이 다르다"가 사는 유일한 자리.** 진 하나당 규칙 하나.
- 예 (재료: `확산(불)` + `응축(물)`, 즉 "퍼지는 불" + "뭉치는 물"):
  - **순환진** (규칙 = 번갈아 순환) → "퍼진 불 ⇄ 뭉친 물" 교대로 나감
  - **융합진** (규칙 = 섞음) → "끓는 물안개" 한 덩이
- 🔴 **손으로 짜는 건 조합마다가 아니라 "이 진은 뭉치들을 어떻게 합치나" 딱 하나씩.**
  불+확산+물+응축의 모든 경우를 일일이 authoring하지 않는다 — 진의 "합치는 성격"만 정한다.
- 🔴 **지금 만드는 게 아니다.** 진별 해석은 나중에 진을 추가할 때마다 손으로 짠다.
  이 설계는 **그 자리를 비워두는 것**이지, 지금 순환진·융합진을 구현하자는 게 아니다.

## 그림

```
┌──── 진 : 순환진   (② 진 규칙 = "번갈아 순환") ────┐
│                                                    │
│    [룬 자리 1]                [룬 자리 2]           │
│   ╭─ 확산 ─╮                ╭─ 응축 ─╮            │  ← 바깥 = 문양 (감쌈, 층)
│   │  불   │                │  물   │            │  ← 안쪽 = 룬 (씨앗)
│   ╰───────╯                ╰───────╯            │
│   = 퍼지는 불               = 뭉치는 물            │  ① 룬마다 감쌈 (전 진 공통)
│                                                    │
└────────────────────────────────────────────────────┘
              ↓  ② 진 규칙이 둘을 합침 (진마다 다름)
        "퍼진 불 ⇄ 뭉친 물" 교대로 나가는 마법
```

- **안쪽 = 룬 · 감싸는 바깥 = 문양** — 자리마다 작은 양파.
- **자리 개수·위치 = 진 모양이 정함** (동그라미 1자리, 순환진 2자리…).
- **양파들을 어떻게 하나로 합치나 = 진 규칙** (②).

진 만들 때 손으로 정하는 것 = **딱 두 가지**:
1. **룬 자리가 몇 개, 어디에** (모양)
2. **그 자리들을 어떻게 합치나** (규칙)

## 확정된 규칙 (대화로 잠근 것)

- **진 = 바깥 껍질(그릇). 안쪽부터 룬 → 문양 → 문양** 순으로 감싸며 나간다.
- **층(밴드) 깊이 = 연산 순서.** 안쪽 층 먼저 해석, 바깥 층이 그걸 감쌈.
- **문양 하나가 층 1~2개를 점유할 수 있다.** 2층 점유 = 그 두 층을 통째로 먹음 →
  거기에 1층짜리 문양 2개를 못 넣는다. (크고 세지만 자리값이 비쌈 = 트레이드오프.)
- **진마다 룬 개수 = 2~6개** (진 만들 때 그 진에 맞게 정함). 진 모양이 룬 자리 수를 정한다.
- **룬 ↔ 문양 짝은 고정 아님.** 대체로 전 조합 가능. 일부 불가 조합은 나중 여지 (지금 안 박음).
- **문양도 진처럼 밑그림(본)으로 손으로 그린다** — 조립 대상이자 탁본 대상. (세68 정체성 유지.)
- **문양이 영향 주는 대상 = 그 문양이 감싸는 안쪽(룬 또는 안쪽 문양 뭉치).**
  룬 자리 위에 놓으면 그 룬을, 바깥 공용 층에 놓으면 안쪽 전체를 감싼다.

## 첫 변형 문양 — 확산·폭발 (M1 콘텐츠, ✅ 확정 세78)

지금 문양(응집·발산)은 **독립 착탄 전개**라 순서가 무의미하다. M1의 순서 실증을 위해 **변형형 문양**
(안쪽 결과를 감싸 바꾸는 연산자) 2종을 정의한다:

- **확산 (퍼뜨림)** — 안쪽 결과를 **여러 갈래/넓게 편다.** (한 줄기 → 부채꼴, 좁은 것 → 넓은 것)
- **폭발 (터뜨림)** — 안쪽 결과를 **한 점에서 광역으로 터뜨린다.** (착탄 AoE)

**순서가 만드는 차이 (M1 성공 기준 = 이게 눈에 보이면 성공):**

| 배치 (안→밖) | 수식 | 결과 |
|---|---|---|
| 불 → 확산 → 폭발 | `폭발(확산(불))` | 넓게 편 뒤 통째로 터뜨림 = **넓은 지역 광역 한 방** |
| 불 → 폭발 → 확산 | `확산(폭발(불))` | 터뜨린 뒤 여러 갈래로 폄 = **작은 폭발 다발이 부채꼴로** |

- 🔴 **수치(퍼짐 각도·갈래 수·폭발 반경·피해)는 전부 balance.tres 시작값, F5로 조인다.**
- ⚠ **이름 겹침 주의**: "확산"은 **바람 룬**이 이미 쓴다(바람 = 상태를 옆 적에 옮기는 확산자, `status_rules`).
  문양 확산(마법을 기하적으로 폄)과 개념이 다르다 — 구현 시 이름 충돌 정리(문양 id는 별도, 표시명 재검토).
- 계약: 확산·폭발도 `GlyphRingDef.motif`가 **새 GlyphCode 값을 참조**하는 방식(세70 규약). `Enums.GlyphCode`에
  값 추가는 되지만 기존 값(GATHER=0/RADIATE=1)은 **밀지 않는다.** 변형 연산자는 착탄 전개(응집·발산)와
  **다른 계열**이라, 발사 해석기가 "전개형 vs 변형형"을 구분해 변형형은 안쪽 결과에 함수처럼 적용한다.

## 남은 조각 — 추천안 (세78 교차 감사 반영 · ⏳ 사용자 최종 확인 대기)

전부 **기존 문서·라이브 코드와 정합되게** 채웠다(감사가 확인한 조립 UI 체인 위에 앉힘). 뒤집고 싶으면 말해라.

1. ✅ **진 등급 = 층 수 (사용자 확정 세78)** — 확정이라 더 안 연다.
   - **진에 등급이 있다. 등급은 오직 층 수만 정한다** (위력·다른 축과 무관).
     `N등급 = N층 = 룬 하나를 감쌀 수 있는 문양 겹 상한`.
   - 🔴 **숫자가 클수록 높다** (1등급 < 2등급 < 3등급 …). **상한 9등급** — 사용자: *"내가 얼마나 확장할지 몰라서"*.
   - **축 두 개로 갈린다**: **진 종류**(일반진·순환진… = 룬 자리 배치 + 합치는 규칙 = 성격) × **등급**(층 수 = 얼마나 깊게).
     같은 종류의 다른 등급이 공존한다 — `일반진 1등급`·`일반진 2등급`·`일반진 3등급`. 파밍 감각과도 맞물림.
   - 🟢 **새 스키마 0 — `JinDef.band_count`가 곧 등급이다.** `.tres` 한 장에 `band_count = N` + 표시명 "N등급"이면 끝.
     (별도 grade 필드를 만들면 band_count와 갈라진다 — 단일 소스 규율.)
   - 1등급(1층) = 1겹뿐이라 **감쌀 순서가 안 생긴다**. **2등급부터 `폭발(확산(불))`이 가능**해진다.
   - ⚠ **기하 한계**: `BAND_RADII = [0.42, 0.68]`로 **지금 2겹까지만** 정의돼 있다. 3등급 이상을 넣으려면 반경 목록을 늘려야 하고,
     🔴 **실제로 손으로 그을 수 있는 겹 수의 상한은 판 크기·정밀도 tolerance가 정한다**(밴드 간격이 tolerance보다 충분히
     커야 함 — 세50 「반경 실측」 교훈). **스키마 상한 9는 확장 여지이고, 실용 상한은 F5로 잰다.**
   - ⚠ 이름 겹침: 게임에 이미 **도안 등급**(`ring_power.grade_of` — 얼마나 잘 그렸나)·**아이템 등급**(`grade_colors.gd` — 희귀도)이
     있다. 진 등급이 세 번째라 UI 표기는 구현 때 정리("3등급 일반진" 식으로 진 이름에 붙이기 추천).
2. **진 규칙(②) 표현** — 추천 = **코드 분기로 시작**(진 id → 합치기 함수). 진이 몇 개 쌓여 공통 패턴이 보이면 그때 데이터로 추출.
   지금 없는 걸 미리 스키마화하지 않는다(YAGNI · 세47 「안 켠 배선」 교훈). ⚠ 위력에 개입하면 `ring_power` 단일 소스.
3. **문양의 "기본 의미"** — 추천 = **문양은 기본 뜻이 있다**(확산=퍼짐, 폭발=터짐). 진 규칙은 **②(여러 룬 합치기)에서만 개입**한다.
   ①의 감쌈 의미까지 진마다 뒤집으면 **손으로 짤 양이 폭발**하고 플레이어도 문양을 못 외운다.
4. ✅ **확산·폭발 = M1 첫 변형 문양으로 확정** (위 「첫 변형 문양」 절). 이후 어휘(응축·관통·가속…)는 후속.
5. **조립 UI 표현** — 추천 = **기존 책 조립 UI(밴드 소켓)를 그대로 쓰고 단계적으로 넓힌다**.
   감사가 확인: 조립 UI 체인(`book_redesign`→`progressive_assemble_gate`→`guide_visual_layers`→`draw_tools_panel`)은
   **내부 정합·라이브와 일치**하고, 이 설계의 감쌈-층은 그 밴드를 토대로 채택한다.
   - **M1 (룬 1개)** = 각도 구분 불필요 → **깊이(밴드 순서)만** 쓴다. 기존 밴드 소켓 UI 거의 그대로. UI 신규 공사 최소.
   - **M2 (룬 2개+)** = 그때 **각도(어느 룬 자리)** 축을 추가 → 「각도 × 깊이」 격자 완성.
   - 🔴 실제 손맛(밴드 간격이 정밀도 tolerance의 몇 배인지 등)은 **F5로만** 정해진다(세50 좌표 실측 교훈).
6. **크게 조립할수록 탁본이 길고 어려워진다** — 추천 = **의도로 남긴다.** 층·문양이 많은 진 = 긴 정밀 탁본 =
   자연스러운 리스크·리워드("센 마법진은 그리기 어렵다"). 세68 정본이 이미 이걸 "의도로 남기면 좋음"이라 적었다.
   ⚠ 다만 **지겨움으로 넘어가는 경계는 F5로 확인**(감사가 남긴 실측 목표).

## 기존 설계·코드와의 관계 (🔴 회귀 정직하게 — architect 리뷰 반영, 세78)

이 설계는 순수 오버레이는 아니지만, **처음 생각보다 이행이 얕다** — architect가 실측으로 밝혔다:
**우리가 "새로 지어야 한다"고 본 "안쪽부터 감싸는 층"이 세70에 이미 밴드(동심원 층) 파이프라인으로
지어져 있다.** 지금은 그 층을 발사 직전에 뭉갤 뿐이다.

- **`takbon_model.md` (세68)** — 상위 루프(파밍→조립→탁본→발사)는 그대로. 이 문서는 그 중
  **"조립본이 어떤 구조인가 · 어떻게 해석되나"**를 확정한다. 세68의 미결 1번(순서=연산)을 "산다"로 답.

  *"폭발(확산) = 넓은 지역 광역 한 방"*은 **수치로는 반대**다 — 서술을 고치든 balance를 조이든
  택해야 한다(손맛 영역이라 F5 튜닝 대상).
- 🟢 **M2 함의**: ②(합치기)를 설계할 때 **세기 보존을 기본으로 삼으면 진 규칙 간 차이도 "모양"으로만
  드러난다.** ②에서 진마다 총량을 다르게 할지(예: 융합진은 합이 세다)가 **M2의 숨은 결정점 5번**이다.

### ⓔ 지금 검증 상태 (M2가 깨뜨리면 안 되는 것)

- 전 스위트 **25종** 그린. M2가 건드릴 그물 = `test_jin_layers_auto`(층 순서·발사 계약·수식) ·
  `test_ring_assembly_auto`(조립 상태기계 계약) · `test_save_auto`(도안 라운드트립 — **2겹 도안 항목 있음**) ·
  `test_ring_design_auto`(RingDesign 계약).
- 🔴 **룬을 다중화하면 `test_ring_assembly_auto`의 룬 계약이 먼저 빨개진다** — 그게 정상이다(계약이 바뀐 것).
  기대치를 갱신하되 **뮤테이션으로 검출력을 다시 증명**해라(세79에 10건 확인한 방식).

**M3 — 문양 2층 점유 · 문양 어휘 확장(확산·응축…) · 진 규칙 데이터화.** 필요해지면.

M1을 먼저 하는 이유: 룬 1개 감쌈이 ②(합치기)의 입력 단위라, ①이 서면 ②가 자연히 얹힌다.

## core 반영 목록 (🔴 리드 전용 — 에이전트 금지, architect 유추)

- 🔴 **다중 룬 자리** — 지금 룬은 `assembly._rune: int` **1개**, `JinDef.glyph_slots`는 **문양 칸**(룬 칸 아님).
  "진 모양이 룬 자리 2~6개" 실현 = JinDef 룬-슬롯 레이아웃 + RingAssembly 다중 룬 보관. **M2 이전엔 불필요**(M1=룬 1개).
- 🔴 **층/감쌈 표현** = `rings` 다겹 재사용 (권장, 스키마 무변경) vs 새 중첩 필드. 권장 = rings 다겹.
- 🔴 **진 규칙(②) id** = "진 id → 합치기 함수" **코드 분기로 시작**(YAGNI, 데이터화는 진 쌓인 뒤).
  진 규칙이 위력에 개입하면 **반드시 `ring_power.gd` 단일 소스에.**
- **EventBus 신규 시그널 = 불필요** (전개는 ring_spell_system 내부에서 닫힘).

## 못박을 계약 (architect, 낮음이지만 필수)

- 🔴 **발사 계약 `Enums.GlyphCode` 안 민다** — 새 문양은 `GlyphRingDef.motif`가 GlyphCode를 **참조**(세70 규약).
  칸 int에 새 의미를 끼우지 않는다.
- 🔴 **감쌈/순서 위력은 `ring_power`가 판다** — 리포트(책)=발사 같은 함수. 진 규칙 위력 감쇠를 복붙하면 갈라짐 재발.
- 🔴 **`to_assembly()` 우회 금지** — 다겹 층 도안도 `score`를 실어야 손그림 위력이 산다(세26).
