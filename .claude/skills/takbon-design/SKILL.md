# 탁본 기획 — 아이디어를 설계로

새 기능·시스템·콘텐츠를 **코드로 착지하기 전에** 사용자와 대화하며 무엇을·왜·어떻게 재밌게 만들지 확정한다.

🔴 **이 스킬은 리드(메인 세션)가 켠다. 서브에이전트에 위임하지 마라.** 이유: 서브에이전트는 사용자와 대화를 못 하고 격리 실행돼 혼자 결정하고 계획서만 뱉는다 — 그게 정확히 사용자가 싫어하는 "혼자 정해서 생각과 다르게" 나오는 원인이다. 대화형 기획은 구조상 리드만 할 수 있다.

<하드-게이트>
**셋 다 통과해야 설계 문서를 쓸 수 있다. 하나라도 못 채우면 착지하지 마라.**

**① 최소 3라운드** — 설계 문서를 쓰기 **전에** 질문↔응답 왕복이 **최소 3회** 있어야 한다.
🔴 **한 라운드 = 질문을 던지고 답을 받는 왕복 1회.** 한 메시지에 질문 넷을 몰아 넣고 "3라운드 했다"고 세지 마라 — **그건 1라운드다.**
🔴 **"이건 간단해서 3라운드가 필요 없다"는 예외가 아니다.** 간단해 보이는 것일수록 검토 안 한 가정이 헛수고를 부른다. 간단하면 **질문을 짧게** 하되 왕복은 세 번 돈다.
🔴 **3은 하한이지 목표가 아니다.** 결정점이 남아 있으면 계속 돈다 — 사용자가 *"이제 됐다"*고 하기 전엔 끝나지 않는다.

**② 결정은 전부 사용자 것** — 설계 문서 §A의 **확정 결정 목록(D1…Dn)에 줄마다 근거(사용자가 실제로 한 말)를 붙인다.**
🔴 **근거를 못 붙이는 줄이 하나라도 있으면 그건 네가 멋대로 정한 것이다.** 착지하지 말고 **그 줄을 질문으로 바꿔 물어라.**
⚠ 이 게이트가 검증 가능한 이유가 여기 있다 — "물어봤나?"는 기억에 기대지만 **"근거 인용이 붙어 있나?"는 문서를 보면 안다.**

**③ 승인 전 구현 금지** — 사용자가 설계를 승인하기 전까지 코드를 쓰거나·스키마를 신설하거나·구현 에이전트(takbon-dev 등)를 부르지 마라.
</하드-게이트>

## 절차 (순서대로)

1. **맥락 파악** — 📖 `docs/GDD.md`(**「게임이 무엇인가」 단일 진실원** — 🔒 읽기만, 수정엔 사용자 허락 필요. ✅ 세96·97에 현행화됐다 — 그리기 폐지가 §2·§3에 반영돼 있다) + `CLAUDE.md` 최상단 + **`docs/DECISIONS.md`**(무엇을 왜 정했나 — 🔴 **방향을 되짚는 기획이면 여기부터**: 이미 정해진 것을 다시 정하려는 건지, 그 결정의 이유가 아직 유효한지가 여기서 갈린다) + **`docs/TODO.md`**(아직 안 한 것 — ⚠ 2026-07-29에 `BACKLOG.md`에서 갈라져 나왔다. **지금 `BACKLOG.md`는 「지난 세션들이 무엇을 했나」다**) + `docs/PROGRESSION.md`(관문) + `docs/takbon-design/`(기존 설계 — **`planned`·`building`·`done` 셋 다 훑되 🔴 `done`을 근거로 새 작업을 시작하지 마라**) + 관련 memory·코드를 읽는다. 탁본은 **부품이 이미 배선돼 있고 "빈 칸"만 있는 경우가 많다**(세27·29 경제가 그랬다) — 새로 짓기 전에 이미 있는지 확인한다.
2. **규모 점검** — 요청이 독립된 여러 시스템을 한꺼번에 담으면(예: "상점·퀘스트·보스 재료·돈을 다") 먼저 조각으로 분해하자고 제안한다. 큰 걸 통째로 설계에 우겨넣지 마라. 조각마다 별도 설계→구현 사이클을 돈다.
3. 🔴 **질문 — 최소 3라운드, 한 번에 하나씩.** `AskUserQuestion`으로 왕복한다. 한 메시지에 질문 하나. 객관식이 답하기 쉬우면 객관식으로.
   **세 라운드의 뼈대**(이건 하한이다 — 남은 결정점만큼 더 돈다):

   | 라운드 | 무엇을 묻나 | 안 물으면 생기는 일 |
   |---|---|---|
   | **1 — 무엇을·왜** | 해결하려는 불편이 정확히 무엇인가. 지금은 어떻게 아픈가 | **엉뚱한 문제를 푼다.** 세101 문 복원이 이 라운드에서 *"엔딩 조건이 원리적으로 성립 안 함"*을 캤다 |
   | **2 — 어떻게 재밌나** | 2~3안 + 트레이드오프. **추천을 먼저** 놓고 이유를 설명한다 | **첫 아이디어로 굳는다.** 사용자가 고를 기회 자체가 없어진다 |
   | **3 — 경계** | **안 하는 것** · 규모 · 성공 기준(무엇이 되면 끝인가) | **범위가 샌다.** 세99 던전이 *"AI가 대략 구현해 놓은 상태"*가 된 경로다 |

   ⚠ **답이 예상과 다르면 되돌아가 다시 물어라** — 라운드 수를 채우는 게 목적이 아니다.
4. **2~3안 제시** — 트레이드오프와 함께. **추천안을 먼저** 놓고 이유를 설명한다(AskUserQuestion 첫 옵션 + "(추천)").
5. **설계 제시 — 섹션별로.** 복잡도에 맞춰 각 섹션 길이를 조절(간단하면 몇 문장). **섹션마다 "여기까지 맞나요?"로 승인받고** 다음으로 간다. 어긋나면 되돌아가 다시 짠다.
6. **설계 문서 착지** — 확정된 설계를 🔴 **`docs/takbon-design/planned/<주제>_design.md`**에 쓴다(기획 문서의 영구 보관소, git 추적). **아래 「설계 문서 형식」의 §A/§B를 반드시 지켜라.** 🔴 리포 루트 `scratch_*.md`에 쓰지 마라 — 그건 옛 관행이고 지금은 이 폴더가 정본 보관소다. ⚠ **일회성 보고서(`docs/_reports/`)와 헷갈리지 마라 — 설계는 영구, 보고서는 지운다.** 🔴 **방향이 갈린 결정(무엇을 왜 정했나)은 `docs/DECISIONS.md`에 한 줄로 올려라 — memory가 아니다**(세107에 memory를 96→4개로 줄였고 「무엇을 했나」는 안 쓴다. ⚠ `STATUS.md`는 세92에 없앴다).
7. **문서 자가 점검** — 새 눈으로 훑는다: 미완("TBD"·빈 섹션)·모순·두 가지로 해석될 애매함·범위 과대. 있으면 그 자리에서 고친다.
8. **takbon-architect 리뷰** — 착지한 설계 문서를 takbon-architect에 넘겨 **계약 위반·회귀 위험·"이미 있는 배선"·도형 플레이스홀더**를 훑게 한다(아래 「리뷰 위임」). 리뷰 결과를 사용자에게 전하고, 지적이 있으면 문서를 고친다.
9. **사용자 최종 검토** — "설계 `<경로>`에 정리·리뷰 완료. 구현 들어가기 전에 한 번 봐주세요." 승인받는다.
10. **구현으로 전환** — 승인 후에만 구현 축에 넘긴다: **`takbon-dev`**(돌아가는 것 — 모듈·Control UI·애니 배선) · **`takbon-vfx`**(보이는 빛 — 발사·착탄·손맛) · **`takbon-art`**(도트 스프라이트 — ⚠ **`takbon-artref`로 레퍼런스를 먼저 받아라. 경로가 없으면 art가 거부한다**). 🔴 **축 목록의 정본은 `CLAUDE.md`「위임 · 일하는 방식」이다** — `takbon-ui`·`takbon-animator`는 세92에 `takbon-dev`로 흡수돼 **부르면 실패한다.**
    🔴 **넘기는 순간 설계 문서를 `planned/` → `building/`으로 옮기고 README 표를 고쳐라**(아래 「3단계 보관」).

## 설계 문서 형식 — §A 게임 기획 / §B 개발 설계

🔴🔴 **한 주제 = 한 파일, 그 안을 두 절로 가른다**(2026-07-29 사용자 확정). 파일을 둘로 쪼개지 마라 — **한 기능의 정본이 두 장이 되면 갈라진다**(이 리포가 세51·84·87에 세 번 겪은 병이다).

```markdown
# <주제>

## §A 게임 기획          ← 사용자와 대화로 확정한 것. 사용자는 여기만 읽어도 된다
1. 무엇을 · 왜            (한 문단. 지금 무엇이 아픈가)
2. 플레이어가 겪는 것      (화면에서 무슨 일이 일어나나)
3. 왜 재밌나              (🔴 잣대 = "조립의 선택지가 늘어나나 / 다르게 조립하면 전투가 종류로 달라지나")
4. 확정 결정 (D1…Dn)      (🔴 줄마다 사용자 발언 근거 — 하드-게이트 ②)

## §B 개발 설계          ← takbon-architect 리뷰 대상
5. 씬·노드 · 시그널 · 데이터(.tres)
6. 계약 · 회귀 위험        (발사·저장·룬 사슬을 건드리나)
7. 착수 순서 (단계 1…n)    (🔴 무엇이 한 원자인지 표시 — 쪼개면 깨지는 묶음)
8. 미결 / 딸린 할 일       (→ `docs/TODO.md`에 이름으로 올린다)
```

- ⚠ **D1…Dn은 이 문서 안에서만 유효한 번호다.** 다른 문서에서 `D3`으로 부르지 마라 — `docs/PROGRESSION.md`에 별개의 `D3`이 있다.
- 🔴 **§A를 건너뛰고 §B부터 쓰지 마라.** §A가 비면 「왜 이걸 만드는가」가 코드에만 남고, 반년 뒤 각하 근거를 못 캔다(세91에 **규격 100% 통과한 구현이 각하됐다** — 이유가 형태였는데 그 판단 근거가 어디에도 없었다).
- 손맛·밸런스 수치는 §B에 확정하지 마라 — *"이 값은 F5로 조인다"*로 남긴다(아래 원칙).

## 3단계 보관 — `planned` → `building` → `done`

🔴 **설계 문서는 상태에 따라 물리적으로 자리를 옮긴다**(2026-07-29 사용자 확정). 상태 이모지로만 갈랐더니 **표가 낡으면 구분 자체가 사라졌다**(세106 실측: 전량 구현된 문서가 「구현 미착수」로 적혀 있었다 — 그걸 읽고 착수하면 **이미 있는 기능을 다시 짠다**).

| 폴더 | 언제 여기 있나 | 누가 옮기나 |
|---|---|---|
| `planned/` | 설계 착지 완료 · **구현 미착수** | 이 스킬(절차 6) |
| `building/` | **구현 중** · 부분 구현 | 리드(절차 10에서 넘길 때) |
| `done/` | **구현 완료** | `takbon-docs` 에이전트 |

🔴 **옮길 때마다 `docs/takbon-design/README.md`의 세 표를 같이 고쳐라** — 그 표가 `ls`와 갈라지면 그 자체가 버그다(README 머리말이 그 규율을 든다).
🔴 **`done/`으로 내리기 전에 「딸린 미결」을 먼저 건져라** — 문서 안에만 있던 미결이 통째로 묻힌다. 정본 절차 = `takbon-docs`.

## 🔴🔴 그래프 프론트매터 — 착지하는 모든 설계문서에 붙인다 (세111)

**왜**: 문서끼리 같은 자원을 두고 **몰래 충돌**한다. 기념비 분모를 `gate_restoration`은 「최종 전 챕터 수」로, `genre_pivot`은 「개방된 문양 종류」로 정했는데 **둘 다 에러 0**이었다 — 충돌 사실이 README 표 셀 안 **산문**에 파묻혀 아무도 못 잡았다. 엣지를 데이터로 옮겨 기계가 잡는다.

```yaml
---
node: <파일명에서 `_design.md`를 뗀 slug>
stage: planned          # 자리와 반드시 같다 — 옮기면 여기도 고쳐라
owns: [monument, ...]   # 🔴 이 문서가 사라지면 **아무도 못 정하는** 것만. 대개 1~3개
needs: [genre_pivot]    # 먼저 확정돼야 하는 노드. 없으면 []
blocked: 첫 조각 미선택   # 착수를 막는 것이 있을 때만
---
```

- 🔴 **`conflicts`는 적지 마라 — `owns` 겹침으로 계산된다.** 겹칠까 봐 일부러 빼면 검출이 죽는다. **사실대로 적어라.**
- 🔴 **어휘는 `tools/docs_audit.py`의 `VOCAB`이 정본이다.** 새 자원은 거기 먼저 넣어라 — `monument`와 `monuments`는 안 겹쳐서 오타가 곧 검출 실패다.
- 검사: `python tools/docs_audit.py` (충돌·죽은 엣지·순환) · `--ready`로 **지금 동시에 착수 가능한 문서**를 본다.

## 탁본 고유 기획 원칙 (설계를 이 잣대로 판단한다)

- 🔴🔴 **코어 재미 = 마법을 「조립」하는 것** — 세83에 **그리기(탁본)가 폐지됐다**(사용자가 세 번 반복해 확정: *"조립이 맞음 모든걸 조립으로"* · F5 반응 *"쉬워서 좋은거 같아"*). 새 기능 기준 = **"조립의 선택지가 늘어나나 / 다르게 조립하면 전투가 종류로 달라지나?"**
  🔴 **정본 둘** = **`docs/DECISIONS.md`「마법 모델」 첫 줄**(*"그리기(탁본)를 폐지했다 — 조립만으로 마법이 맺힌다"*, 세83 — **왜**·되돌리는 법까지 거기 있다) + **`docs/GDD.md` §2**(심장 = 「조립 + 그 결과가 화면에서 달라지는 것」 · 새 기능 판단 기준 둘).
  ⚠ **세107에 memory가 96→4개로 줄면서 이 줄이 가리키던 `takbon-core-fun-drawing`·`takbon-drawing-abolished`가 둘 다 사라졌다.** 남은 memory 4개엔 기획 근거가 없다 — 🔴 **기획 근거를 memory에서 찾지 마라.**
  ⚠ **폐지는 스위치다**(`balance.skip_drawing` 기본 true) — 코드는 안 지웠고 되돌리면 손 긋기가 살아난다. 그래서 「그리기 자산을 파괴하는 설계」는 피하되, **잣대는 현재 확정 방향(조립)을 따른다.** ✅ **GDD는 세96에 따라왔다** — 손 긋기는 §3의 **휴면 각주**로 내려갔고 「그리는 것 = 심장」은 더는 GDD에 없다.
  🔴 **다음 위험 = "쉽다" → "얕다"**: 조립이 **유일한 재미 축**이라 부품(문양·진·룬 어휘)이 얇으면 곧 얕아진다 — **어휘 확장이 최우선 기획 축이다.**
- **"주지 말고 얻게"** — 챕터/보상은 재료 쳇바퀴가 아니라 **새로 조립할 것**(새 룬·문양·진 = 코어 재미 확장)으로 흘러야 한다.
- **다르게 조립하면 전투가 "종류"로 달라지나** — 세43 진단(자유도 구멍): 축들이 스칼라(세기)만 바꾸면 재미가 없다. 새 축은 전투 방식을 바꿔야 한다. 🔴 이미 있는 「종류」 축 = **층(밴드) 순서 = 연산 순서**(M1) · **룬 2개 = 원소 반응**(M2) · **문양 `behavior`**(M3).
- **회귀 위험을 구조로 0** — 기존 계약(발사·저장·룬 해금 사슬)을 **안 건드리는** 설계를 우선한다(세36 퀘스트가 순수 오버레이로 회귀 0을 만든 게 모범).
- **데이터 주도** — 가능하면 "새 X = .tres 한 장"으로 떨어지게(takbon-rules §4). 단일 소스(`ring_power`·`Db`)를 늘리지 마라.
- **손맛·밸런스는 설계가 아니라 사용자 튜닝** — 수치를 확정하려 하지 말고 "이 값은 플레이하며 조인다"로 남긴다. 손맛은 헤드리스로 못 재고 **사용자가 직접 쏘고 맞아 봐야** 정해진다(폐지 전엔 "마우스로 그려봐야"였다 — 지금 손맛의 자리는 발사·피격·연출·조립 리듬이다).
- 🔴 **생명체·프롭은 도형 플레이스홀더로 설계하지 마라** (사용자 확정 세54). 새 적·캐릭터·아이템·프롭은 `takbon-art` 아트 명세(경로·크기·프레임·방향)를 설계에 넣는다. 예외 = 절차적 VFX·가이드선.
- **YAGNI** — 안 시킨 기능·과설계는 뺀다.

## 핵심 태도

- **한 번에 질문 하나** — 몰아치지 마라. 🔴 **몰아 묻는 건 라운드를 아끼는 게 아니라 라운드를 없애는 것이다**(하드-게이트 ①).
- **추천을 먼저** — 2~3안을 늘어놓기만 하지 말고 "나는 이걸 추천, 왜냐면…"을 앞에 둔다.
- **점진 검증** — 섹션마다 승인받고 넘어간다.
- **유연하게** — 어긋나면 되돌아간다. 사용자 생각과 다르게 굳히는 게 이 스킬이 없애려는 문제다.
- 🔴 **혼자 확정 금지** — 결정점마다 사용자에게 묻는다. 이 스킬의 존재 이유다.
- 🔴🔴 **「이건 당연하니까」가 가장 위험한 순간이다** — 멋대로 정하는 건 대개 어려운 결정이 아니라 **네가 자명하다고 느낀 것**에서 나온다. 착지 직전에 **"내가 사용자에게 안 묻고 정한 게 무엇인가"를 한 번 세어라.** 세어서 나오면 §A의 D 목록에 근거가 안 붙는다 — **그 자리가 곧 질문거리다.**

## 리뷰 위임 (절차 8단계)

착지한 설계 문서를 takbon-architect에 넘겨 훑게 한다. Agent 도구 프롬프트에 반드시:

```
설계 문서 `docs/takbon-design/planned/<주제>_design.md`를 리뷰만 해라(구현·새 설계 금지).
🔴 §A(게임 기획)는 사용자가 확정한 것이니 방향을 뒤집지 마라 — **네 리뷰 대상은 §B(개발 설계)다.**
확인: ① takbon-rules 하드 계약 위반 ② 회귀 위험(발사·저장·룬 사슬 등 기존 계약 건드림)
③ "이미 있는 배선"인데 새로 짓자고 한 것 ④ 도형 플레이스홀더로 착지시킨 생명체·프롭
⑤ 스키마·시그널 신설 필요분(리드가 core에 반영해야 함으로 표기).
결과를 `docs/_reports/<주제>_review.md`에 써라(채팅 보고는 리드에게 안 온다 — 파일로).
승인 | 지적사항(섹션·이유) 형식으로.
```

⚠ 리뷰 파일(`docs/_reports/<주제>_review.md`)은 **일회성**이다 — 리드가 읽고 반영한 뒤 지운다. 영구 보관하는 건 설계 문서(`docs/takbon-design/`)뿐이다. ✅ `docs/_reports/`는 **gitignore**라 안 지우고 넘어가도 리포엔 안 남는다(세96 — 그전엔 루트 `scratch_*.md`라 `git add -A`에 딸려갈 수 있었다).

리뷰 결과 파일을 리드가 읽고, 지적이 있으면 설계 문서를 고친 뒤 사용자에게 최종 검토를 청한다.

## 이 스킬을 끝내는 상태 = 구현 착수

이 스킬의 종착점은 **사용자 승인 + 구현 축(`takbon-dev`·`takbon-vfx`·`takbon-art`)으로 위임**이다. architect 리뷰는 중간 게이트지, 종착점이 아니다.
